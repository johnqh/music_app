# music_app (Moosiac)

> **Git policy — never auto-commit or auto-push.** Leave your work in the working tree.
> Run `git commit`, `git push`, `gh pr create`, or `scripts/push_all.sh` **only when the user
> explicitly asks in that turn**. Approval for an earlier change does not carry forward, and
> finishing a task is not permission to commit it.

The Moosiac web app: routing, pages, and UI only. One of seven repos in the Moosiac family — see [Related Projects](#related-projects). All business logic (score model, commands, rendering adapters, Zustand store) lives in `@sudobility/music_lib`, which is platform-free; every platform-bound capability — audio playback, XML parsing, file export, the MIDI codec — is an interface in `@sudobility/music_types` implemented by `@sudobility/music_io`, which serves web and React Native from one import via a `react-native` export condition. All networking goes through `@sudobility/music_client`; the backend (OpenAI proxy + project persistence) is the sibling `music_api` repo. See [docs/architecture.md](docs/architecture.md) for the full six-repo picture and request flows.

## Tech Stack

- React 19, TypeScript (strict), Vite, React Router
- **Tailwind CSS** (`@sudobility/design`'s preset, `darkMode: 'class'`) — **no MUI/Emotion** (removed in T13; see Gotchas)
- `@sudobility/components` / `@sudobility/building_blocks` / `@sudobility/auth-components` for shared UI primitives (buttons, dialogs, spinners, sign-in forms)
- Zustand app store, VexFlow rendering (windowed **canvas** via `CanvasScoreRenderer`, one canvas, no per-glyph DOM), soundfont playback (`js-synthesizer`, **not** Tone.js — see Gotchas) — all via `@sudobility/music_lib`, never imported directly here
- `@tanstack/react-query` for server-state (dashboard project list) via `@sudobility/music_client`'s hooks
- Firebase Auth (real backend) / an in-process e2e shim (`VITE_E2E=1`)
- Bun for scripts; Vitest + Testing Library + jsdom for unit/component tests; Playwright for e2e

## Package boundaries

Each package has one job, and `src/__architecture.test.ts` enforces it rather than trusting the rule to be remembered:

- **`music_types`** — the model, its Zod schemas, and the pure primitives both frontend and backend need (pitch and tick math, the score factory, quantization, ties, voice allocation, vocabularies, picker options, readout formatting, `outOfRangeNoteIds`), and **every shared type and closed vocabulary**: codec option/result types, the audio-import extensions and MIME table (`AUDIO_IMPORT_EXTENSIONS`, `AUDIO_MIME`), the `ScoreFiles`/storage contracts, and the frontend vocabulary (edit modes and `EDIT_MODE_OPTIONS`, theme and device-pref shapes, toasts, `LayoutMode`, `PAPER_OPTIONS`/`ORIENTATION_OPTIONS`, inspector/toolbar/context-menu/docs vocabularies, input shapes, copy contracts, generation drafts, export formats and the formats table). No dependencies, hooks or async.
- **`music_codecs`** — every score file format that carries notes: MIDI, MusicXML, tracker modules and the app's own `.moo` project file, plus the filenames written for them. Free of `music_lib`, `music_io`, `vexflow` and `tone` by its own guard test, because `music_api` (backend) and the frontend both decode MIDI and neither may depend on the other.
- **`music_client`** — the network: the typed client for `music_api`, React Query hooks, generation job and snapshot hooks.
- **`music_io`** — **files and audio files**: the `open*`/`save*` layer over the codecs (`createScoreFiles`), reading an audio file's name or size (`audioMimeFor`, `isLongAudio`), _audio_ file formats (mp3/wav), the filesystem, XML parsing, MIDI input.
- **`music_player`** — everything that makes sound: the transport (`IMusicPlayer`), both synth engines, plan building and offline rendering.
- **`music_drawing`** — canvas and keyboard geometry and presentation: the score canvas interface (`ScoreCanvas`), hit testing, which keys are lit (`litKeys`, `samePitchSet`, `playingPitchesForTrack`), print layout (`printPlan`), render themes. It does not decide what a press _means_.
- **`music_editing`** — editing, and nothing else: the editing store and every operation that changes a score, including what a press means (`classifyPress`, `routeScorePress`). No playback binding, documents, export planning, docs content or device prefs. Depends on neither `music_codecs` nor `music_player`.
- **`music_lib`** — frontend business logic above editing: the composed app store, per-document stores, autosave, the player binding (`bindPlayer`) and playback adapter, export planning (`planExport`), the unsaved-work guard (`decideClose`/`decideQuit`), documentation content (`DOCS_TOPICS`, `RESOURCE_GROUPS`, `hostOf`, `monogramFor`), generation request builders, credits, device prefs (`resolveThemeMode`, theme, developer mode and settings, keyboard, font size, language). Re-exports `music_types` and `music_editing`, so a name from either resolves through `@sudobility/music_lib` too.
- **`music_app`** — UI, and only UI.

Three rules decide where a new name goes, and they are the user's: **type definitions and vocabulary live in `music_types`**; **pure helpers used by both frontend and backend live in `music_types`**; **`music_editing` is for editing only and depends on neither `music_codecs` nor `music_player`**. A move between packages leaves **no re-export behind** in the old home — each library has a guard against the moved names — so an import that stops resolving after a library update is pointing at an old home, and the fix is the import, not a shim.

**The model lives in `music_types`, once.** It used to live in both — 128 modules duplicated between `music_types` and `music_lib`, most differing only by an import path, three (`note-commands`, `structure-commands`, `relocate-commands`) genuinely diverged because new commands had been added on the music_lib side only. `music_lib` now re-exports `@sudobility/music_types` wholesale from its own index, so every existing `@sudobility/music_lib` import still resolves, and its `domain/` folder is down to two modules that genuinely cannot move: `note-entry` (reads a store selector, which would drag zustand into music_types) and `pitch-drag` (reads a layout constant). The rule for what may live in music_types is exactly four things — it must work on both the frontend and the backend, add no dependencies, contain no hooks, and contain no async code. `replacement-region.ts` uses `measures[length - 1]` rather than `.at(-1)` for the first of those: the package targets ES2020 so the server can consume it, and `.at` is ES2022.

Nine modules had already drifted into music_app — `note-entry`, `lyric-syllables`, `duration-modifiers`, `duration-selection`, `range-select`, `pitch-drag`, `snapshot-tree`, `selection-editing`, `tap-to-note` — none of which touched React, the DOM or layout geometry. They now live in music_lib. The guard has an explicit `ALLOWED_NON_UI` list so an exemption is a decision somebody makes on purpose, and it checks deep imports against each package's **declared `exports` map** rather than a pattern — music_io legitimately publishes `/web`, `/rn`, `/mocks` and two `/rn/*` tables, and a hand-written allow-list of those would go stale the moment it adds one.

**Canvas geometry belongs to `music_drawing`; app layout geometry stays in the app.** The line is the canvas edge. Anything that reasons about the _drawn score_ — where a note went, which measure or track a point lands in, what pitch a stave position means, where the playing measure sits, the colours VexFlow draws with — is `music_drawing`'s, because the canvas is what that package owns and because two apps now draw the same score. So `hit-test`, `track-gutter`, `note-drag`, `playback-scroll`, `note-colors`, `playhead` and `render-theme` all live there.

Anything that reasons about the _app around_ the canvas stays here: `autoscroll` takes a pointer near the edge of a scroll box and returns a scroll delta, which is a fact about this app's scroll container and not about the score.

This used to read "geometry stays in the app", on the grounds that a question about a pointer is UI work. That held while there was one app. It stopped holding when the React Native app needed the same answers: what it actually produced was a tap that could only resolve to a _measure_, because the note bounding boxes lived on the other side of a boundary drawn in the wrong place.

## Gotchas

- **The documentation is a page, and most of it is generated.** `/:lang/docs/:topicId` is master-detail — the topic list stays put while a topic scrolls, and the topic is in the URL so a link into one section is shareable. It is deliberately **outside the auth gate**: somebody deciding whether to sign up has to be able to read what the app does. Prose lives in the locale files through `docs-content.ts`, which holds structure and i18n keys only, so a Chinese reader gets Chinese documentation — `locale-parity.test.ts` enforces that, and `docs-content.test.ts` catches the half parity cannot see, since a key missing from **both** locales is perfectly consistent and renders as its own name. **Three sections are built from live data rather than described in prose**: the instrument table reads `gmInstrumentRows` over `GM_CATALOGUE` (so it cannot go stale, and it puts the `basis` column in front of a reader), the shortcut table reads `shortcut-table.ts`, and the format tables read `formats.ts`. Prose about a table is a copy of that table.
- **The Resources page's links and the docs structure are `@sudobility/music_lib`'s,
  and the format tables are `@sudobility/music_types`'** — the native app renders the same three,
  and a forty-two entry list transcribed into a second app is forty-two chances
  for the two to disagree about what this product can open. What stays here is
  the one part a library cannot hold: the vendored icons, read through Vite's
  own glob. Adding a link is still four steps, they just start upstream.
  Precisely: `DOCS_TOPICS`, `docsTopic`, `docsGroupLabelKey`, `RESOURCE_GROUPS`,
  `hostOf` and `monogramFor` are music_lib's (documentation content is frontend
  business logic, not editing); the vocabularies and types they are built from —
  `DOCS_GROUPS`/`DocsGroup`, `SHORTCUT_GROUPS`/`ShortcutGroup`, `Resource`/
  `ResourceGroup`, `IMPORT_FORMATS`/`EXPORT_FORMATS`/`FormatEntry` — are
  music_types'. `SHORTCUTS` itself stays in music_editing beside the bindings it
  lists. `src/features/docs/formats.ts` and `src/pages/resource-links.ts` re-export
  from those homes so this app's pages did not have to change.
- **The Resources page is grouped by importer, and adding a link is four steps.** It answers "I have nothing to open — now what?", so the useful half of an entry is not the link but _which importer the file feeds_: the sections are Sheet music / MIDI / Tracker modules / Recordings / Bulk collections / Instruments / Formats, and each states its route **once**, in the section header. It carried the route per card when there were five links; at forty-two that is forty-two repetitions of "Opens with Import → MIDI" and a section heading nobody can navigate by. Links live in `resource-links.ts` (data, apart from the JSX, the way `docs-content.ts` is), so adding one means: the entry, an `en` and a `zh` string under `resources.link.<key>`, and a re-run of the icon script. `resource-links.test.ts` fails on a key missing from both locales — the half `locale-parity` cannot see — and on an orphaned string left behind after a link is removed. The host under each name is **derived from the URL** and never typed; a page that is nothing but outbound links should say where each one goes, and a hand-written host is the one field free to disagree with the href above it.
- **The site icons are vendored, not hotlinked, and the files on disk are the lookup table.** `scripts/fetch-resource-icons.ts` walks apple-touch-icon → sized `rel=icon` → manifest → `/favicon.ico` → Google's favicon service and writes `src/assets/resource-icons/<key>.png|svg`; the page reads them back through `import.meta.glob`, so nothing can _claim_ an icon that is not there. Forty-two `<img>` tags aimed at forty-two other people's servers would tell each of them who is reading the page and would break one tile at a time as those sites reorganise. Four sites publish no icon at all — CPDL, MIDIWORLD, Modland and colinraffel.com each answer `/favicon.ico` with an error page or a 1×1 GIF — and get a one-letter monogram rather than a flag somebody has to remember to clear. Two things are deliberate and look like bugs. Every icon sits on the **same light chip in both themes**, which is the one place this app ignores dark mode: these are thirty-eight logos drawn by thirty-eight people and a good few are solid black on transparent, so inheriting the surface makes them vanish when the page goes dark. And `sips -Z` resamples in **both** directions, so the script caps rather than resizes — upscaling a 32px favicon to 128 costs six times the bytes to store the same information and hands the browser a blur (measured: 412K → 232K).
- **`build.assetsInlineLimit` exempts `resource-icons` on purpose.** Vite base64s any asset under 4KB into the JS, and most of these are 16 or 32px favicons well under it — 25 of the 38 were, adding ~49KB to the main bundle. There is no route-level code splitting here, so that lands on every visitor to pay for one page few of them open, and base64 gzips worse than the bytes it encodes. Remove the exemption and the bundle silently regains the weight.
- **`Grid`'s `cols={{ sm: n }}` is the BASE column count, not the 640px breakpoint.** `@sudobility/components` emits `sm` as an unprefixed `grid-cols-n` and only `md`/`lg`/`xl` as prefixed classes, so `{ sm: 2, lg: 3 }` means two columns on a phone. Write `{ sm: 1, md: 2, lg: 3 }` for the usual one-then-two-then-three. This is invisible in the prop name and silent in review — the page simply reads cramped on mobile. `HomePage`'s `{ sm: 3 }` still has it: three columns at 390px.
- **The toolbar glyphs are shared with the native app, as data.** Two apps draw
  a sharp sign, and two drawings of it would drift the moment either was tuned —
  invisibly, since a glyph a pixel out is not something a test notices or a
  reader can name. So `notation-icons.tsx` stays the authoring form (React, with
  the geometry computed from shared constants) and
  `NOTATION_ICONS` in music_types is **generated** from it by
  `scripts/extract-notation-icons.mjs | scripts/generate-notation-icon-art.mjs`.
  Re-run that after changing an icon; `notation-icon-art.test.ts` fails if the
  two disagree, comparing the numbers each contains rather than their markup,
  because the two forms order attributes differently and only the geometry
  matters. It was generated rather than transcribed because the icons compute
  their paths from constants and template literals — copying them by hand is
  hundreds of chances to get a number wrong.
- **The shortcut list is shared with the help dialog, and checked against the bindings.** It used to live inside `ShortcutHelpDialog` as a hand-typed copy of music_lib's key map, and had fallen **six entries behind it**: `Shift+F` fermata, `Shift+A` arpeggiate, `Shift+G` glissando, `Shift+O` octave bracket and both hairpins were bound, worked, and appeared in no list — a reader had no way to discover them. The bindings now publish `SHIFT_MARK_KEYS`, and `shortcut-table.test.ts` fails if any bound mark is missing from the list.

- **One fact, one declaration — and `src/__single-source.test.ts` enforces it.** A constant restated in a second package agrees with the first right up until one of them is edited, and nothing fails when they part: the build is clean, the types match, and the only symptom is a wrong sound or a picker quietly missing an entry. Measured across the family, 23 UPPER_CASE constants were declared in more than one repo — `CC_VOLUME` three times, `DYNAMICS` four, `C_MAJOR` five, and `DEFAULT_TIME_SIGNATURE` in four places under two names. The guard reads the list of names **from music_types at runtime** rather than restating it, because a check against duplication that duplicates what it checks would drift like everything else; its `ALLOWED` list is empty on purpose, so an exemption is a decision somebody writes down. Two shapes matter beyond the constants themselves. **A closed vocabulary is declared as an array and the type read off it** (`export const DYNAMICS = [...] as const; export type Dynamic = (typeof DYNAMICS)[number];`) — a TypeScript union has no runtime form, so anything that must _validate_ a value has to write the list out again, which is exactly how music_api's decoder came to check generated music against its own private copy. **A label or option list keyed by the vocabulary is a `Record<T, ...>`, never a parallel array** — a record fails to compile when a member is added, an array silently goes on offering the old set; that is why the inspector's picker lists are `ACCIDENTAL_OPTIONS`/`ARTICULATION_OPTIONS` built from the vocabulary rather than `ACCIDENTALS`/`ARTICULATIONS` retyped. Test fixtures follow the same rule: the score fixtures live once, in `@sudobility/music_types/test`, and a package that needs a rendering fixture of its own re-exports them and adds to them.

- **No MUI/Emotion anywhere** (T13) — dark mode is a Tailwind `dark` class on `<html>`, toggled by `applyDocumentTheme()` from an effect in `App.tsx` that also listens for OS `prefers-color-scheme` changes when `themeMode === 'system'` (`themeMode` and `developerMode` are music_lib's device-prefs slice, composed into the web app's store; they are no longer in music_editing's ui slice). `ScoreEditorView`'s VexFlow render-theme colors are still literal hex strings (`LIGHT_RENDER_THEME`/`DARK_RENDER_THEME`) — VexFlow draws straight to the canvas context, not CSS, so this is deliberate, not a leftover.
- `VITE_E2E=1` swaps Firebase Auth for a fixed-identity in-process shim (`e2eBackend()` in `config/initialize.ts`) — never enable it outside Playwright/dev.
- No business logic belongs in this repo. If you're about to write score math, a new command, an adapter, or a store slice, it almost certainly belongs in `music_lib` instead.
- **Canvas notation view**: `ScoreEditorView` draws through music_lib's `CanvasScoreRenderer` into a single viewport-pinned canvas over a full-height interaction/spacer div; drawing only the visible systems per scroll/resize frame IS the virtualization (O(visible), unbounded score sizes). All interactions are geometric (`hit-test.ts` over the drawn window's bbox maps) — there are no `vf-*` DOM elements. jsdom tests stub `HTMLCanvasElement.getContext` with music_lib's `createMock2DContext` (`src/test/setup.ts`); e2e resolves note/measure ids to click coordinates via the dev/e2e-only `window.__scoresmith` handle (`e2e/helpers.ts`).
- **Note state is color, not rectangles**: there is no highlight overlay (it and `paintHighlights` were deleted). `buildNoteColors` builds an `eventId -> NoteColorRole` map (`normal`/`selected`/`regenerated`/`playing`) that the renderer applies with VexFlow `setStyle` per note; stave lines use `staveActive`/`staveInactive` by active track. **A track that is not the active one dims whole** — notes, beams, ties, stave lines, clef and time signature all step down to `noteInactive` (the clef/time-sig via the context colour set per stave in the draw loop, since those draw from the context rather than the stave's style). Two deliberate exceptions: a selected/regenerated note keeps its state colour on every track (cmd-shift-click selects across tracks, so dimming would hide what the user just did), and the active track keeps `noteNormal` rather than darkening further, because a state colour is what marks a note as needing attention and an ordinary note on the active track needs none. **Playing is not among them: only the active track's sounding notes light up.** They used to light up everywhere, by the same reasoning as selection — but selection is something you did on purpose across tracks, and playback is not. On a large score the lit notes then scattered across whichever parts happened to be sounding, which reads as random rather than as a playhead, and the one track you were reading went dark whenever it rested. The piano keyboard already showed the active track alone; the notation now agrees with it. The filter is in `colorsWithPlaying`, on the `trackId` the engine reports with every sounding note. With no `activeTrackId` set nothing dims at all — `notesDimmed` is deliberately not `!isActiveTrack`. Colors live in `LIGHT_RENDER_THEME`/`DARK_RENDER_THEME` in `ScoreEditorView.tsx` — literal hex, since VexFlow draws to canvas and never resolves CSS vars — and `PianoRollView` imports the same pair so a note means the same thing in both. A selection change therefore redraws notation, which is cheap: `computeLayout` is cached and not invalidated by color.
- **Following playback never fights the reader's vertical scroll** (`playback-scroll.ts`). It used to scroll to `boxForMeasureIndex(plan, 0, ...)` — track 1's stave — so on a multi-track score every wrap threw whatever track you were watching off the top of the viewport. Page mode now carries your _offset into the system_ across to the next one (track 3 at the top stays track 3 at the top); continuous mode is one wide system, so it follows horizontally and never touches `scrollTop` at all. Horizontal following happens **only in continuous mode**, where it clears `TRACK_INFO_WIDTH * zoom` as well as the margin — the gutter is painted _over_ the sheet at the viewport's left edge, and targeting the margin alone parked the playing measure behind the track info (measured: the caret was occluded on 96 of 120 samples; 0 after). **Page mode does not scroll horizontally at all**: `computeLayout` fits every system inside `width / zoom` (both margins come out of the packing budget), the scroll box is `overflow-x-hidden` there, and `playbackScrollTarget` returns `left: 0` — a horizontal scroll in page mode could only slide the sheet under the gutter. `totalWidth` used to mirror `leftMargin` as its trailing margin, which carries the gutter's reserved column, so page mode overhung its viewport by a phantom `TRACK_INFO_WIDTH`; `layout.test.ts` now pins `totalWidth <= width` across widths and zooms.
- **A write uses the effective edit mode, and nothing writes it back.** Stack on a part that cannot play a chord (asked through the track, so a kit is not read as the Violin at its address) is replace: `selectEffectiveEditMode` in music_editing is what chord entry, paste, the toolbar's pressed button and a note drag's collision all read. The toolbar used to write the effective mode back into the store from an effect, because the library's write paths read the stored one — a render late, and it threw away the reader's choice, so switching back to a piano did not give stack back. The stored `editMode` is now left alone. On a monophonic part that means a new note _replaces_ what is at the caret rather than being refused as a chord, and replace does not count the notes it removes against the polyphony limit.
- **Insert uses the caret, not the selection.** `resolveInsertTarget(score, activeTrackId, caretTick)` puts the new note in the _active track_ at the caret. It used to derive the target from the selection, which meant clicking empty staff — which moves the caret and clears the selection — sent the next note to the very start of the score. A caret past the last barline clamps into the final measure rather than failing. **Insert Note advances the caret** past what it wrote (`insertDefaultNoteAtCaret`), on both apps, so pressing it repeatedly lays out a line rather than stacking notes on one tick.
- **Drag a selected note to change its pitch** (`pitch-drag.ts`). A press on the _one_ selected note starts a pitch drag instead of a selection box — requiring it to be selected first is what keeps an ordinary click-and-drag across the staff a box select. Movement is diatonic (`shiftDiatonic`), by staff positions rather than semitones, so the note follows the pointer across E-F and B-C; `STAVE_POSITION_HEIGHT * zoom` is the pixels per position. The whole gesture commits as **one** `changePitchCommand` on release, so undo restores the pre-drag pitch rather than stepping back through it. The live preview redraws only when the step count changes (~10 times a drag, not 60/s) because a new score identity invalidates the cached layout; `scoreWithPitch` shares every branch it did not touch for the same reason.
- **The score is immutable while the transport plays.** Every editing route reaches the store through `dispatchCommand`/`undo`/`redo`, and each refuses a command whose `kind` is `content` while `state === 'playing'` — so the lock is one guard per entry point rather than a rule each caller remembers. **Mixing is exempt**: mute, solo, volume and pan are `kind: 'mix'` and reach the engine live through `PlaybackEngine.applyMix`, because muting a part while listening is how an arrangement gets listened to. `changeTrackPropsCommand` classifies itself from its own patch — mix only if _every_ key in it is — since it carries a partial patch and serves both purposes. `insertNoteAtCaret`/`insertChordAtCaret` refuse early too, so the caret and duration state do not advance as though something had been written; auditioning a piano key still sounds, only the write on release is suppressed. UI-wise, content affordances go `disabled` while playing — the inspector reads `selectEditLocked` (the **whole Note tab**, and every content field on the Bar and Score tabs; only the mix controls stay live), the toolbar reads `selectToolbarAvailability` (Add/Delete bar, Enter Lyrics and Replace included); Copy and the duration buttons stay live because the first only reads and the second also sets the default insert duration.
- **A score arriving from outside stops the transport first.** A generation result landing or a snapshot opening replaces the score without going through `dispatchCommand`, so the lock never sees it — and `PlaybackController` would then treat it as a mix change and keep playing the old score out of the engine's queue. Opening a snapshot goes through music_lib's `adoptOutsideScore(store, score, playbackController, { serverUpdatedAt })`, which stops first; the generation reload has no score to hand over (it re-reads the project), so it still calls `playbackController.stop()` itself before `openProject`. That is what keeps "while playing, the only score change is a mix change" true by construction, which is the invariant the controller's no-reload branch rests on.
- **The caret moves by keyboard, and it takes Alt to do it.** `Alt+←/→` steps it by the toolbar's current note value, `Home`/`End` go to the bar's edges and `Cmd+Home`/`Cmd+End` to the score's. Alt is the disambiguation: the bare arrows already move the selection and transpose it, and typed note entry needs the caret moved without disturbing either — letters write at the caret and step it forward, so going back to fix the note before last cannot require the pointer. `End` lands just _inside_ the bar rather than on the next barline, because it has to be a position a note can still be written at.
- **A MIDI keyboard plays into the same handlers as the on-screen one.** `MidiInput` is a `MusicIo` capability (`web-midi-input.ts`; React Native and the mocks get `createUnsupportedMidiInput`, which reports `isSupported()` false so the feature simply is not offered). Events are routed through `PianoKeyboardView`'s own `pressKey`/`releaseKey` rather than writing notes directly, so everything the on-screen keys already do comes with them — the note sounds while held, a chord struck together is grouped, the held time becomes the duration, the caret advances. A second write path would have been a second copy of those rules to keep in step. **A note-on at velocity 0 is a note-off**: many keyboards send that instead of a real one, and taking it literally leaves the note sounding forever. Access is requested lazily on the first `listDevices`, without sysex, so nobody is prompted on page load for a permission they may not need.
- **Two voices on one stave are told apart by their stems** — upper up, lower down, in `measure-content.ts`. A single voice keeps VexFlow's own per-note choice, which is what an engraver would do; forcing a direction there would point half the notes the wrong way. Before this a second voice drew identically to the first, so there was no way to see which line you were editing, which is the whole reason a second voice exists.
- **Lyrics are typed through the line, not one field at a time.** A syllable lives on its note (`NoteEvent.lyric`), because that is what a lyric is — text belonging to a notehead, which moves, copies and deletes with it; a parallel list of syllables would need re-aligning after every edit that changed the note count. Entry is `LyricEntryBar`, which takes over one note at a time: **space** ends a word, **hyphen** ends a syllable _within_ one, **Enter** finishes, **Shift+space** steps back over a typo. The `syllabic` join (`begin`/`middle`/`end`) is _derived_ from those keystrokes rather than asked for — a writer knows they are mid-word — and it is what draws the trailing hyphen and fills MusicXML's `<syllabic>`. The bar reads the current syllable from the **store**, not from the notes array it was handed: that array is a snapshot from when entry began, so stepping back over a word just typed showed an empty field until it looked at the live score. `single` is the default and is never stored. The importer no longer warns that lyrics are dropped, because they are not.
- **Repeats play, and the score tick stays canonical.** `Measure.repeatStart`/`repeatEnd` are two independent flags rather than a span, because a `:|` with no matching `|:` repeats from the start of the piece — a real marking, not an error to prevent. `endingNumbers` is carried on **every** bar of a volta, with the bracket's ends derived from whether the neighbour has the same numbers, so deleting a bar shortens the bracket instead of leaving one pointing at nothing. `changeRepeatsCommand` applies at the same measure **index across every track**: a `:|` on one stave and not the others is a score that reads differently depending on which part you play from.
- **Performance time and written time are different numbers, and exactly one place knows it.** `repeatPlayOrder` expands a score into the bars a player actually performs; `performanceTimeline` turns that into segments mapping performance ticks to written ticks, and `playbackPlan` lays the notes (and the metronome) out along it. **The `PlaybackController` translates at both boundaries and nothing else does**: `onPositionTick` converts the engine's performance tick to a score tick before it reaches the bus, and `seek` converts the other way. So the caret, the following-scroll, the bar/beat readout and the position scrubber all still receive a score tick and none of them knows repeats exist — which is why adding this touched four consumers' worth of behaviour without touching four consumers. A score with no repeats yields the **identity timeline**, so its playback is unchanged to the tick. Second-pass notes get a `#2`-suffixed id, because the caret lights a note by id and one written note sounding twice must not light both places at once. `seek` targets the **first** performance of a written tick: clicking bar 3 and pressing play starts the first time through, which is what "play from here" means to somebody reading the page.
- **A chord symbol is stored as typed, not as a parsed chord.** `C-7`, `Cmin7` and `Cm7` are one chord written three ways, and `F/A`, `Bb7#11` and `Cmaj7(add13)` all have to survive being entered — so `NoteEvent.chordSymbol` keeps the string and nothing a player writes is refused or silently rewritten. Only the **root** is parsed, for MusicXML's `<root-step>`, which is the unambiguous part; the rest rides as `kind="other"` with the typed text, because mapping every dialect of "minor seventh" onto MusicXML's enumeration is a dictionary that is wrong for somebody. It prints **above** the stave — the opposite side from the lyric and the dynamic, which is what keeps all three legible on a lead sheet. Attached to a note, like a lyric, since the chord changes _at_ a note; a change during a held note has to wait for the next onset, which is the one thing this shape cannot express.
- **A grace note hangs off the note it decorates, not the voice.** It takes no time from the bar, so as an event of its own it would have to be excluded from every sum that checks a measure adds up — validation, rest filling, quantization, the VexFlow voice. `NoteEvent.graceNotes` means none of those change at all, and the ornament moves, copies and deletes with its principal, which is what a player expects. `toGraceNoteCommand` takes the note _out_ of the voice and leaves a rest of the same length, so the bar still totals; ornaments the source itself carried travel with it, rather than being silently dropped in front of the new principal. **They sound**, and they borrow from the principal rather than the bar: `flattenScoreNotes` lays them before it and starts it that much later, capped at half its length — an ornament that swallowed its own note would be a rewrite — so every following note stays exactly where it was. VexFlow's `GraceNoteGroup` is a modifier on the principal, which is the same relationship the model stores. MusicXML writes them as `<note>` elements carrying `<grace/>` with no `<duration>`, before their principal; import holds each one until the next sounding note, the same shape of problem as a dynamic.
- **A tuplet is derived, never stored.** Three notes each two thirds of a plain value _are_ a triplet, which is exactly what `tupletGroups` reads — so there is no `tupletId` on a note to fall out of step with the durations when one of the three is deleted, retimed or pasted over. A run that no longer sums to a plain value simply stops being drawn as one, which is the truth rather than a stale bracket. Only whole threes group: a run of four is one triplet and a leftover, and bracketing the leftover would claim a grouping the music does not have. Rests count as members — a triplet with a rest in the middle is still a triplet. **MusicXML needs the written value and the sounding one to disagree**: a triplet eighth is `<type>eighth</type>` with a `<duration>` two thirds of an eighth's divisions, reconciled by `<time-modification>`. `notateDuration` only knows plain values, so handing it the scaled length classified a triplet eighth as the nearest thing it had — a 16th — and the note came back a third short; the exporter now types it from the _unscaled_ length and keeps the real duration. Import needs no arithmetic for the common case, since `<duration>` is already scaled; the `<type>`-only fallback applies the ratio itself.
- **Beams are derived; only the disagreement is stored.** `NoteEvent.beam` holds `break` or `none` and is absent on almost every note — the same reasoning as the tuplet next to it, since a run of eighths under one beat _is_ a beam, and storing the grouping would let it fall out of step with the durations the moment a note is retimed, deleted or pasted over. `break` starts a new group at that note (what vocal writing needs, where the beam follows the syllables rather than the beat); `none` takes the note out of beaming so it draws its flag. **The renderer segments rather than groups**: `beamsFor` in music_drawing splits the voice at each `break`, drops each `none`, and hands each run to VexFlow — so inside a run the default beat grouping, the time signature and the dotted values all stay VexFlow's job. Two things about that are load-bearing and were both wrong first. A run opened by an override is beamed as **one explicit group** (`groups: [new Fraction(WHOLE_RUN, 1)]`), because `Beam.generateBeams` otherwise re-applies beat grouping from the run's _own_ first note — "break at note 1" then came back as a beamed pair plus a stray flag instead of the group of three that was asked for. And a `break` on the **first** note of a voice is a deliberate no-op: there is no group before it to end, and reading it as "group explicitly from here" silently rebeamed whole bars as one. Both are pinned by tests, and both were found by printing actual beam sizes rather than by reading the code. There is deliberately **no `join`**: beaming _across_ a beat is the one change segmenting cannot express, and supporting it would mean reimplementing beat grouping rather than reusing the renderer's — left out rather than half-built.
- **Beaming round-trips through MusicXML, and that is why the grouping is a shared derivation.** MusicXML has no "break here": it wants a complete `begin`/`continue`/`end` run, so writing it at all means knowing every group — and the exporter lives in `music_codecs`, which must not depend on a rendering engine (`music_api` decodes MusicXML server-side, where there is no VexFlow). So `beamGroups` in music_types owns the rule, and the exporter writes from it. Compound time groups by the **dotted** beat (6/8 is two groups of three, and beaming it in twos is the classic way to make a jig unreadable); 3/8 is deliberately excluded from that branch, since one dotted-quarter beat spanning the bar is simple time in practice. **Import stores the difference, not the file**: it asks `beamGroups` what it would do unaided and records only the disagreement, because importing every `<beam>` verbatim would fill a score with overrides that say nothing and would be re-derived on the next edit anyway. That reconciliation is a **fixpoint, and it resolves breaks before unbeamed notes** — both learned from a failing round trip. A break leaves the note before it alone, so the file writes no `<beam>` on that note; read naively that looks like a deliberate flag, and the `none` it stores then _cancels the break_ (a break whose preceding run is empty is a no-op), so the bar came back regrouped. Only the primary `number="1"` beam is written and read: secondary beams follow from `<type>`, and stating them wrongly is worse than leaving them inferred. **The renderer still delegates grouping _within_ a run to VexFlow** rather than reading `beamGroups` directly — reimplementing beat grouping, dotted values and time signatures in the renderer to remove one duplicated rule is the worse trade — so `beam-agreement.test.ts` in music_drawing pins the two against each other across every override case. If VexFlow's defaults ever move, that fails instead of the exported file quietly ceasing to match the page. **The one thing that cannot round-trip is a file that beams _across_ a beat**: `break` and `none` only split and remove, so such a passage imports with our grouping rather than the file's. That is the same missing `join` the model documents, and closing it means owning a second grouping rule instead of deriving one.
- **A slur is not a tie, and the model keeps them apart.** `slurStart`/`slurStop` sit beside `tieStart`/`tieStop` and mean something different: a tie joins two notes _of the same pitch_ into one sounding note and `joinTiedNotes` merges their durations; a slur groups a run of _different_ pitches as one phrase and joins nothing. Keeping them in separate fields is what stops phrasing from changing playback. `toggleSlurCommand` takes the whole selection rather than a flag per note — the caller says "slur these" and the command picks the endpoints **by tick**, so a selection built by shift-clicking around a phrase is still that phrase, and a start can never be created without its stop. Fewer than two notes is refused: a phrase mark over one note means nothing. Drawn with VexFlow's `Curve`, culled to drawn staves and guarded per curve exactly as ties are — a mark reaching an off-screen stave throws `NoYValues` inside VexFlow. MusicXML writes it _inside_ `<notations>`, unlike a dynamic, because it is a property of the note rather than an instruction at a point in the measure; the importer no longer reports `<slur>` as unsupported.
- **A Standard MIDI File carries what the transport played.** `exportMidi` used to walk the score itself, so an exported file held the _stored_ velocity and duration and none of the score's expression — measured on a passage marked `ff` with accents, the transport played velocity 127 and the file held 80. Dynamics, hairpin ramps, articulation weight and shortening, and grace notes were all absent; ties were the only thing that walk rejoined. It now takes its notes from `flattenScoreNotes` — the traversal live playback and offline audio export already share — and its tempo map from `fermataTempoMap`, so a file written from a paused score actually holds its pauses. The old `collectTrackNotes`/`maxVoiceCount` helpers existed only for that walk and are gone. **Anything added to `flattenScoreNotes` now reaches all three outputs**, which is the point of having one traversal; before this, MIDI was the consumer that silently drifted.
- **Repeat navigation: the places are flags, the instruction is an enum, and the order they mean is derived.** `segno`, `coda`, `toCoda` and `fine` are _places_ a bar carries — independent, because a bar can hold the coda sign and a `Fine` at once — while `jump` is the _instruction_, sitting on the bar at whose end it is obeyed. `toCoda` and `coda` are deliberately separate flags: the bar you **leave** from is not the bar the coda begins at. The six jumps are one enum rather than a direction composed with a target, so only combinations a player actually meets are expressible. **The rule that is invisible in the notation and easy to get backwards: `Fine` and `To Coda` mean nothing on the way out.** A player reads straight past both until a jump has sent them back; honouring `Fine` on the first pass stops the piece halfway through, which is roughly half the score. `repeatPlayOrder` carries a `stopAt` that is `null` until a jump sets it, which is what encodes that. A jump is taken **once** — after obeying it the player reads through it — or the piece never ends. A broken score still plays: a `dal segno` with no segno falls back to the start and an `al coda` with incomplete marks plays to the end, because that is what a reader does. Because it all lives in `repeatPlayOrder`, playback, the performance timeline and the caret needed no changes — the same seam the repeat barlines already used. MusicXML round-trips through `<direction>`, reading the **`<sound>` attributes** (`dacapo`, `dalsegno`, `fine`, `tocoda`) rather than the `<words>` beside them, since the words say "D.C. al Fine" in as many spellings as there are engravers; the words are consulted only to tell `al Fine` from `al Coda`.
- **A double or final barline is a style, and the repeat barlines are not.** `Measure.barline` holds only `double` and `final`; absent is the ordinary single line, which is almost every bar. The `|:`/`:|` deliberately stay on `repeatStart`/`repeatEnd` — they are two independent flags rather than one choice, and a bar can both close a repeat and end the piece. Where both land on one bar the **repeat wins**, in the renderer and in the exporter alike: a `:|` is an instruction a player acts on, and drawing a double bar over it would silently remove a repeat from the performance. `changeBarlineCommand` applies at the same index **across every track**, like the repeats, because a double bar on one stave and not the others is a score that reads differently depending on which part you play from. MusicXML writes it as `<barline location="right"><bar-style>light-heavy|light-light</bar-style></barline>`.
- **A hairpin is the change between two levels, and it is shaped like a slur.** `hairpinStart`/`hairpinStop` sit beside `slurStart`/`slurStop` because a wedge is the same kind of object — a span with two endpoints written over a run of notes — and the _start_ carries the direction, since that is what decides which way it opens. Kept apart from `dynamic`, which marks a level beginning at a note: a hairpin can run between two dynamics, from one with nothing after it, or over notes carrying no dynamic at all. `toggleHairpinCommand` picks the endpoints **by tick** like the slur, refuses fewer than two notes (a wedge over one note has nowhere to open to), removes the span when the **same** direction is applied again and flips it when the **other** one is — which is what reaching for the other button means. **It sounds, as a ramp**: `hairpinVelocities` moves velocity linearly from the level in force at the opening to the level in force just _after_ the close, because that is how a player reads it — the wedge takes you to the next marking. Where there is no next marking it moves **one dynamic step**, walking the same ladder a written marking would have used; leaving it flat would make the mark silent, and ramping to full or to nothing would turn an unmarked detail into the loudest thing in the piece. Resolved in `flattenScoreNotes` beside the dynamic and the articulation, so live playback and offline export cannot disagree, and the note's own written velocity still survives as a deviation on top. Drawn with VexFlow's `StaveHairpin` **below** the stave where the dynamics already are, culled to drawn staves and guarded per wedge exactly as ties and slurs are. MusicXML writes it as a `<direction>` like a dynamic rather than a `<notations>` child like a slur — a wedge is an instruction at a point in the measure — and the **close is written _after_ the note it covers**, unlike the opening: a `<direction>` sits at a point in the bar, so a stop emitted ahead of the closing note would end the wedge at that note's onset and leave it uncovered.
- **An octave bracket is a display lens, not a transposition.** The model stores **sounding** pitch, so `8va` means "these were written an octave lower to keep them on the stave" — `ottavaScore` in music_lib shifts the noteheads to where they are _written_, the opposite way from the bracket, and returns its input object untouched when no bracket exists so `computeLayout`'s identity cache is unaffected. A lens over the whole score rather than a shift inside the renderer, for the reason `writtenScore` is one: the layout and everything measured from it see the same score, so a drawn note and its staff position agree by construction. Applied **before** `writtenScore` and in **every** mode, unlike an instrument's transposition — a bracket is part of the notation rather than a way of reading it. MusicXML's `<octave-shift>` names the direction the **notes** move, which is the opposite of the sound: `8va` is `type="down"`. Both inversions (the lens and the export) are pinned by tests, because each is invisible on inspection and wrong by exactly an octave.
- **Note entry inverts the display lenses, in the reverse order they were applied.** `displayScore` is `writtenScore(ottavaScore(score))`, so `soundingPitchForDrawn` (`hit-test.ts`) takes the transposition off first and the bracket second, and only then stores. Without it a click stored whatever was _drawn_ as though it were the sound: an octave out inside an `8va` — in **every** mode, since `ottavaScore` is unconditional — and a whole tone out on a B-flat clarinet read in written pitch. Both were silent, because the note then drew exactly where it had been clicked and only sounded wrong. The bracket in force at a tick comes from `ottavaShiftAt` in music_types, which is the tick-keyed counterpart to the id-keyed `octaveShifts` the lens itself uses: a new note has no id to look up. The round-trip is asserted as **pitch, not spelling** — written-to-sounding preserves the sound exactly and respells freely, which is measured and deliberate.
- **A slide is a span; a finger belongs to a notehead.** `glissandoStart`/`glissandoStop` mirror the slur, so an exported `<glissando type="start"/>`/`stop` pair round-trips as what it is and a slide across a rest cannot be written by accident; VexFlow has no `Glissando`, so it draws as a `StaveLine` between the two notes, which is what a glissando is on the page. `fingering` is a **string**, not a number: piano writing uses 1-5, guitar adds `T`, and editions write `1-2` for a substitution — a picker would refuse two of those. It is per key on a chord, unlike every other mark here, because each notehead has its own finger, and it exports inside `<technical>`, where MusicXML keeps anything about _how_ an instrument produces a note.
- **Marks are on Shift, and the wedges look like themselves.** `Shift+F` fermata, `Shift+A` arpeggiate, `Shift+G` slide, `Shift+O` 8va, and `Shift+<`/`Shift+>` for the hairpins — the one pair nobody has to memorise, since those are the wedge symbols. Shift is the only modifier left: bare letters are note entry, digits are note values, and `isModified` reserves Cmd/Ctrl for the browser. They are handled **above** the note-entry block deliberately: `Shift+G` arrives as `"G"`, which `pitchForLetter` would otherwise happily write as a note. A test pins exactly that.
- **A rolled chord is a flag per note, because there is no chord to hang it on.** `NoteEvent.arpeggiate` is set on each member, since a chord here is several `NoteEvent`s sharing a tick — which is also MusicXML's shape, where `<arpeggiate/>` appears on every note of the chord rather than once. The renderer adds VexFlow's `Stroke` **once**, on the first key, because the wavy line is drawn beside the whole chord; adding it per member stacks one line per notehead. On a single note it draws nothing — there is one notehead to roll through — and the command deliberately still _sets_ the flag there rather than refusing, so selecting a bar and rolling its chords does not fail because one beat happens to be a single note.
- **A dynamic is a level, and the note's velocity is its deviation.** `NoteEvent.dynamic` marks the note a level _begins_ at and is in force until the next marking on that track — so marking one note `f` makes a passage loud, and there is nothing to apply to the notes between. `flattenScoreNotes` resolves it into velocity, which is the single traversal live playback and offline export already share, so the two cannot disagree about how loud a bar is. The written velocity survives as an offset from the default: an unmarked score plays exactly as it did before dynamics existed, a default note under `ff` plays at `ff`, and an accent inside a quiet passage stays an accent. Overwriting velocity outright — what most notation software does — would have made the inspector's Velocity field silently inert the moment a passage was marked. Drawn with VexFlow's `Annotation` rather than `TextDynamics`, which is a tickable and would need a voice of its own aligned to the notes. MusicXML writes it as a `<direction>` _before_ the note, because that is what it is: an instruction at a point in the measure, not a property of a notehead.
- **A declared warning that cannot fire is a lie in the contract.** `MusicXmlWarnings` is filled in by the host — music_app hands over a translated string per key — so when the importer _gains_ support for something, the call site that warned about it disappears and the key is left behind: still required of every host, still translated, and impossible to ever see. That happened five times (`ornaments`, `clefChangeDropped`, `graceNotes`, `lyrics`, `tuplets`), and twice the opposite way, where a warning that _should_ have gone through the contract was written as a **hardcoded English string** inside music_lib — defeating the whole point of the contract, since a Chinese reader then gets English. `warning-contract.test.ts` reads `import.ts` and fails on any declared key with no `warnings.text.<key>` call site; it found the `unsupportedTime` literal on its first run. Source-scanning rather than fixture-driven on purpose: a fixture proves a warning _can_ fire, but proving one _cannot_ would need a fixture per branch.
- **A missing translation is invisible, so it is tested for.** i18next falls back to the English string, which looks like a working app right up until a reader hits it — that is how 42 strings shipped untranslated in the Chinese build, every MusicXML warning and every project template among them. `locale-parity.test.ts` pins both halves: the two locales define exactly the same keys, **and** every zh string actually contains CJK. The second check is the one that matters — key parity alone passes happily when English is copied across as a placeholder. `SHARED_BY_DESIGN` lists the handful that are the same in both on purpose (MIDI, MusicXML, App Store — a Chinese reader looking for the MIDI import is looking for the word "MIDI").

- **A string with no key is invisible to every parity test there is, and the web shipped fifteen of them.** `locale-parity` compares the two _locales_; it cannot see a label written in English straight into the JSX, because there is no key to be missing. The note-value and accidental pickers rendered their options that way — `'Whole note'`, `'Double flat'` — so a Chinese reader chose a note length in English, and the web had no `duration` or `accidental` group at all while the native app had both, translated. Others were the pitch-display toggle, the inspector toggle, the keyboard collapse, `Voice N`, the MIDI wizard's clef column and the duration tooltip. Grep for `aria-label={'`, `aria-label={\`` and `ariaLabel: '` before adding a control; the fix is always a key, never a literal.

- **The picker vocabularies carry their own i18n key, and getting it wrong prints the key.** `ACCIDENTAL_OPTIONS`, `ARTICULATION_OPTIONS` and `ORNAMENT_OPTIONS` in music_types each publish a `labelKey` — that is the point of them, so two apps' pickers cannot offer different sets or different words. Building a list from the vocabulary and then labelling it from a local table defeats it: this app's ornament picker read `t(option.labelKey)` while its locale carried `ornament.inverted-mordent`, the model's kebab-case spelling, where the library asks for `ornament.invertedMordent` — so the menu read "ornament.invertedMordent" and nothing failed, because a key missing from **both** locales is perfectly consistent. `music_app_rn`'s `cross-app-parity.test.ts` now checks every published key against both apps and both languages, which is where that has to live: only a test that sees both hosts can see it at all.

- **The reader is shown a _bar_; the code keeps `Measure`.** Both words are standard — "bar" is British, "measure" American, and strictly the bar is the _line_ and the measure the span between two of them, which is why even American English writes "barline". The shared libraries had already drawn that line and the UI had not: `Measure` is the model type (`measureSchema`, `findMeasure`, `addMeasureCommand`) while `bar` is the human-facing number and position (`barNumberAt`, `barBeatForTick`, `formatBarBeat`, `indexOfBarNumber`, `goToBarFromInput`), and the distinction is load-bearing — `barNumberAt` exists _because_ a measure index is not a bar number, a pickup having an index and no number. The copy meanwhile used both interchangeably **inside single sentences**: "click a measure number above a system to select that bar", "the measure grid is shared across tracks; a bar is the same bar on every stave". 34 strings now say bar. The one that still says measure is `musicXmlWarn.unsupportedMeasureElement`, which quotes MusicXML's `<measure>` element by name. Chinese needed no change at all: 小节 covers both, and all 89 zh strings already used it. **Keys keep the model's word** — `inspector.replaceMeasures` reads "Replace Bars" — because a key is code and the object is a `Measure`. One thing outside this repo still says it: `music_api` writes usage rows referencing "N track-measures", which is server copy.

- **The inspector's labels are `inspector.*`, and the toolbar's are `editor.*`.** The same field carried two keys for a while — `editor.octave`/`inspector.octave`, `editor.velocity`, `editor.tieStart`, `track.pan`, twenty-eight in all — because this app grew the panel out of the toolbar and the native app wrote it fresh. Two keys for one label is two strings to translate and two to keep in step, and the drift is silent. `editor.voice` is the one deliberate survivor: the toolbar's Voice _group_ and the panel's Voice _field_ are different labels that happen to read alike.

- **The two apps' copy is pinned against each other, and the exemptions are written down.** 798 keys are the same key in both apps and nothing shares them — the libraries hold no strings in any language, which is what lets a Chinese reader get Chinese documentation. `music_app_rn/src/i18n/cross-app-parity.test.ts` pins them from the native side (only that direction: this app's suite must not need a checkout of that one, and it skips when the sibling is absent). Three checks, and the first is the sharp one: **where the English agrees, the Chinese must agree too** — a key whose English is identical and whose Chinese is not is a translation fork with nobody's decision behind it, and six had accumulated (`断音`/`断奏` for staccato, `临时记号`/`变音记号` for an accidental). English differences go in `WORDED_DIFFERENTLY` with a reason; a pointer tooltip and a touch hint may legitimately differ, and "measure" versus "bar" is listed there as **undecided**, which it still is.
- **A pickup is a bar that is not counted, and that is the whole model.** `Measure.pickup` is a flag rather than "measure 0 is short", because those are different things — a short bar mid-score is a deliberate irregular bar and keeps its number. Its shortness lives where it always did, in `durationTicks`, which a `Measure` has always carried independently of its time signature; validation sums voices against `durationTicks`, so it needed no change at all. The visible consequence is numbering, and **nothing computes `index + 1` any more**: `barNumberAt` skips pickups and answers `null` for one (not 0 — a pickup has no number, and the renderer draws nothing there, which is what an engraver does), while `indexOfBarNumber` is its inverse. The canvas gutter, MusicXML export, `barBeatForTick` and `tickForBarBeat` all go through them, so the number in the inspector, the number a player reads and the bar "go to bar 33" lands on are the same 33. `setPickupCommand` applies to **every track** — the measure grid is shared, and a pickup on one stave only is a score whose parts disagree about where bar 1 starts — and it is offered on bar 1 alone. This is MusicXML's `implicit="yes"`, read and written as such; an imported pickup takes its length **from its content** rather than from the time signature, since sizing it by the signature imports an anacrusis as a full bar padded with rests, which is a different piece of music.
- **A clef change is stored on the bar it happens at, and resolved in one place.** `Measure.clef` marks only the _changes_; absent means "carry on with what is in force", and `Track.clef` is the clef the part **opened** in. Storing changes rather than a clef on every bar keeps a part that never changes clef byte-identical to what it was before, and means inserting or deleting a bar cannot strand a clef that was only ever inherited. **Nothing reads `measure.clef` directly** — `effectiveClef(track, index)` in `effective-clef.ts` walks back to the last change, and `clefChangesAt` says where the clef visibly changes. Both the renderer and `pitchAtStavePoint` go through it, which is what stops the notation and the note-entry geometry from disagreeing: they used to share `track.clef`, and a hit test resolving a bass bar in treble places a clicked note a sixth from the line under the pointer — a bug that looks like a rounding error and is not. Bar 0 is never a "change": it is where the clef is _established_, drawn as part of the system header, so `changeMeasureClefCommand` routes it to the **track** clef instead (and through `changeClef`, so crossing into or out of percussion still reinterprets the program). Setting the clef already in force **removes** the marking rather than storing one that would print nothing, so "clear" and "set to the current clef" cannot produce two scores that look identical. Per **track**, unlike `changeRepeatsCommand` which applies across every track: a repeat barline that differed between staves is a score that reads differently depending on which part you play from, but a left hand crossing into treble says nothing about the right. A system starting after a change restates the clef **in force**, not the track's. VexFlow absorbs the mid-system glyph the same way it already absorbs a mid-score key change, so no layout width work was needed. Import no longer drops the change — the `clefChangeDropped` warning was removed from `MusicXmlWarnings` rather than left unfired, and note that `MeasureState` now keeps `clef` (in force) apart from `firstClef` (what `Track.clef` takes): merging them makes an imported part adopt whatever clef it happened to **end** in.
- **A transport readout floors the beat; the inspector's position field does not.** `barBeatForTick` returns a _fractional_ beat on purpose — the inspector's position field is editable and a note can legitimately sit on beat 2.5 — so anything that merely _shows_ a position must put it through `wholeBarBeat`/`formatBarBeat` first. Both live in `music-vocabulary.ts`, beside `barBeatForTick`, because two apps draw this readout and the flooring is a display rule rather than a fact about the score. This shipped broken: the readouts used to call `measureBeatAt`, which floored internally, and replacing it with `barBeatForTick` — the right move, since the old one numbered bars `index + 1` and miscounted every score with a pickup — silently handed them the raw fraction. The web transport renders `${bar}.${beat}`, so it printed **`1.1.3333333333333333`** into a 40px box thirty times a second and snapped back to `1.2` whenever the position happened to land on a beat; that is what "the bar and beat jumps a lot" looks like. **The React Native app was unaffected because it had written `Math.floor(at.beat)` inline** — which is the tell: the same calculation existing in two apps means one of them is eventually wrong, and the one that is right gives no warning about the one that is not. Both now call the shared formatter, and the web readout carries `tabular-nums` besides, since proportional figures make `1.1` and `1.4` different widths and the centred text shuffles on every beat even once the fraction is gone.
- **An ornament is a sign, not the notes it stands for.** `NoteEvent.ornament` stores `trill`/`mordent`/`inverted-mordent`/`turn` rather than the alternation a player would produce, because the realisation depends on period, tempo and taste, and expanding it would make the ornament impossible to remove or re-read. It sits beside `graceNotes`, not instead of it: grace notes spell out exactly what is played, and a note can carry both — which is how an ornament with a written-out termination is notated. **VexFlow's two mordent codes are the reverse of the words a musician uses**, and mapping them by name draws both backwards: `'mordent'` produces the `ornamentShortTrill` glyph (the _unstroked_ upper mordent) while `'mordent_inverted'` produces `ornamentMordent` (the stroked one that is simply "a mordent"), so `ORNAMENT_CODE` in `convert.ts` deliberately crosses over where MusicXML's `<mordent>`/`<inverted-mordent>` read straight across. Verified against the constructed glyph codes, not the docs; `'trill'` is not a code VexFlow knows at all and throws inside the constructor — it is `'tr'`. Import reads `<ornaments>` and **no longer warns**: the `ornaments` warning was removed from `MusicXmlWarnings` entirely rather than left in place, because a warning that can no longer fire is a lie in the contract. A sign this model does not carry (`<wavy-line>`, `<tremolo>`, `<schleifer>`) still warns, and `<accidental-mark>` deliberately does not — it qualifies a sign rather than being one. **Playback does not realise ornaments**, and unlike the fermata that is a mild gap rather than a missing half: the sign is primarily notational, and most notation software leaves it silent too.
- **A fermata is not an articulation, and it has its own field.** `NoteEvent.fermata` sits beside `articulation` rather than joining the enum, because the enum is single-valued and a fermata over an accented final chord is ordinary notation — folding it in would have made the two mutually exclusive. It is a boolean, not a duration: how long a pause is held is the performer's judgement, which is the whole point of the marking. `toggleFermataCommand` toggles the **whole selection together**, reading the state from whether _every_ selected note already has one, so a partly-marked selection becomes fully marked instead of inverting note by note. Drawn with VexFlow's `Articulation` at `a@a` — **always above the stave**, which is what an engraver does in single-voice music; the inverted `a@u` belongs to the lower part of a two-voice texture, not to any stem-down note (known simplification: a lower voice gets its pause above too). Deliberately _not_ chosen from the note's stem direction, which is the obvious wrong answer: `StaveNote.getStemDirection()` reports `Stem.UP` for **every** pitch at construction — the real direction is resolved later during formatting — so keying off it silently inverts every fermata in the score. MusicXML writes it inside `<notations>` and _outside_ `<articulations>`, which is how that format separates them too, and only on the segment a tied note **ends** on, so one pause does not print as a row of them. **It plays, as a local slowing rather than a longer note** (`fermata-tempo.ts`). Stretching the note and shifting the rest is the obvious model and the wrong one: the score tick _is_ the playback tick, and the caret, the following-scroll, "play from here" and the position scrubber all rest on that identity. A tempo dip changes none of it — the notes keep their written ticks and simply take longer to elapse, which is what a fermata means to a player anyway. **That is also why the caret needed no work**: it dead-reckons between position reports through a `TempoMap`, so a map that slows down slows the caret with it; building the caret's map from the plain `score.tempoMap` would send it gliding past the hold and snapping back, the exact stall-and-jump its interpolation exists to prevent. `playbackPlan`, `renderEvents` and the caret all read the one derivation, so the transport, the exported file and the screen cannot disagree about how long a pause lasts — the caret gets it from the same pure function rather than through the bus, so same score in, same map out. Overlapping holds **merge**, and not to stop them compounding (they do not: each reads its reduced tempo from the _original_ map): it is for spans of different lengths, where a quarter held in one part would otherwise restore full tempo in the middle of a whole note held in another. A score with no fermata gets its own `tempoMap` array back **by identity**, so nothing about an unmarked score is even recomputed.
- **An articulation is a length and a weight, and it sounds.** Staccato, accent, tenuto and marcato were modelled, drawn, exported and imported long before anything played them, so a passage marked staccato sounded exactly as long as a legato one. `articulation.ts` in music_lib resolves each marking into a `lengthFactor` and a `velocityDelta` — two axes because that is what the four markings say: staccato is about length (half), accent is about weight, marcato is both (which is the only thing separating it from an accent), and tenuto is the full length it would have had anyway. Resolved in `flattenScoreNotes`, beside the dynamic and for the same reason: it is the one traversal live playback and offline export share. **It applies on top of the dynamic, never instead of it** — `effectiveVelocity` produces the level, the articulation is a further offset on that, so an accent inside a quiet passage stays an accent rather than being flattened to a fixed loud velocity. **Shortening never moves anything**: the note releases early but still _occupies_ its written length, so every following note starts where it did and the bar still adds up — which is what keeps this a performance detail rather than an edit, and why the score is not rewritten as short notes plus rests (the other way to make staccato audible, and one that would make the marking impossible to remove). A grace note takes the **pre-articulation** velocity, because an accent belongs to the note it is written on and not to what leads into it. **Tenuto is deliberately near-inaudible** and that is the honest answer: it means "hold the full value" and an unmarked note is already held its full value, so the alternative was shortening _every_ unmarked note to give one rare marking something to contrast against — which would change the playback of every score ever written here.
- **Notes are typed as well as clicked.** Letters `A`–`G` write that pitch at the caret, digits `1`–`6` choose the note value (whole through 32nd, preserving the dot or triplet already on), `.` dots it, `R` inserts a rest, `T` ties, `Cmd+A` selects everything, and `N` toggles note input. The letter's **octave is the one nearest the previous note** (`nearestOctaveFor` in `note-entry.ts`) — typing C after B gives the C a semitone above, not the C a seventh below — and without that rule letter entry can only write a scale from C4. Entry keys deliberately take **no modifier**, so a browser or OS shortcut can never be mistaken for a note. Before this the only fast path was the piano keyboard: `Insert note` writes C4 and leaves you transposing with the arrow keys.
- **Note input is a mode, because a click cannot mean two things.** With `ui-slice.noteInput` on, a click on a stave writes a note at that pitch instead of moving the caret; off, the caret behaviour is exactly as it was. Clicking to place a note and clicking to aim the caret are both needed, and the caret is what selection ranges, insertion and "play from here" are all aimed with — so it stays the default. The pitch comes from `pitchAtStavePoint` (`hit-test.ts`) over `STAVE_TOP_LINE_OFFSET`, **the same constant the renderer draws the stave with**, so it agrees with what is on screen by construction rather than by a matched guess. Placement goes through the caret — seek, then `insertNoteAtCaret` — so target resolution, the edit lock and the caret advance are the code the toolbar and the piano keyboard already use.
- **The inspector says note values, bars and key names, never ticks or fifths.** `Duration 480` and `Key (fifths) 2` state the storage format; the reader is looking at a quarter note in D major. The conversions live in `music-vocabulary.ts` — in **music_types**, which music_lib re-exports, because it is music theory rather than panel code and because there are two apps drawing these panels now — and `durationNameForTicks` answers `null` for a length no single notehead spells (a tie join or an import can make one), which the picker shows as Custom rather than relabelling as the nearest name. Voice is counted from 1 to match the toolbar's own Voice 1 / Voice 2 buttons; the same note used to read as "Voice 1" on the bar and `0` in the panel. **`panReadout` is there too, and used to be here**: `features/tracks/pan-readout.ts` was three lines this app owned until music_app_rn's property sheet gained the same row and transcribed them — which is the moment a display conversion stops being a detail of one panel and becomes a fact both apps have to agree on.
- **The published page plays its own score.** `PublishedView` binds the player to its own store with music_lib's `bindPlayer` and unbinds and stops on leave. It used to press play on the app-wide store, which played whatever project was open — or nothing. Its share link is `publishedSnapshotUrl`, never `window.location.href`. **It hands the editor's caret back.** The caret is the one shared playhead: adopting the published score starts it at the top (so the page plays from its beginning), and the page's playback and its stop on leave move it further — so the page reads the caret on mount and `moveTo`s it back last on unmount. `ProjectRoute` does the same around its stop-on-leave, because a stop homes the playhead to 0 and the project is still open to come back to; without both, leaving the editor for the dashboard or a published link put the reader back in bar 1. `setScore(score, { resetPosition: false })` was the other option and does not cover it: the page's own Play would still move the playhead from wherever the editor left it.
- **The score's title and composer are the Score tab's, and are not the project name.** `metadata.title` names every exported file and fills MusicXML's work title; `project.name` names the row it is stored in. `renameProject` deliberately does not touch the score, so before the Score tab existed a project renamed after creation kept exporting under whatever its template was called — rename "String Quartet" to "Wedding March", export, still `String Quartet.mid`. Composer had no path at all, which left every exported and published score anonymous.
- **Tempo changes anywhere, not just at the start.** The transport's BPM field always edits `tempoMap[0]`; the Measure tab's `Tempo here` writes an event at that bar's tick, so a piece can slow down or change at a rehearsal point. It shows the tempo _in force_ — inherited from an earlier bar when this one sets none — so it is never blank and never lies, and `removeTempoCommand` drops the change again. Both fields commit through music_editing — `commitBarTempo` for a bar, `commitOpeningTempoText` for the transport — which clamp to `MIN_BPM`/`MAX_BPM` and write **nothing** for an untouched or emptied field, so blurring an inherited tempo no longer leaves an undo entry behind. The starting tempo is never removable: a score with an empty `tempoMap` has no tempo at all.
- **Shift-click the measure gutter to select a span.** A plain click still selects one bar on the active track; shift extends from the bar clicked last, so "bars 3 to 12" is two clicks rather than ten — which matters because Replace Measures and regeneration both work on a span, and picking one out was the slowest part of using them. The anchor is held in a ref, not state: it is read inside the click handler and must never cause a render. Extending twice from one anchor grows and shrinks the range rather than walking it, the way every list behaves. `Cmd+Shift` still means "the same bar across every track", which is a different question and keeps its own modifier.
- **Caret-anchored interaction**: the red caret IS `playback-slice.positionTick` (no separate state), which is why "play from the caret" needs no plumbing. Click = caret + active track + clear selection; note click also selects it; shift-click toggles additively; cmd-click selects caret→click on the active track, cmd-shift-click across all. Measure selection lives only in the measure-number gutter above each system (`measureIndexAtGutterPoint`). `PlaybackController.togglePlay` clears the selection on the →playing transition only. **What a press means is music_editing's** (`classifyPress`, `routeScorePress`, `selectForContextMenu`, `startPointerGesture`, `applyBoxSelection`), shared with the native app; the view only hit-tests. Cmd-click selects to `scoreCanvas.tickAt(point)` passed as `pointTick`, **not** the hit's tick — a hit exists only inside a measure and its tick falls back to 0, so reading it made a cmd-click between systems do nothing.
- **Active track**: `ui-slice.activeTrackId`, read through `selectActiveTrackId`, which falls back to the first track when unset or stale — so "one track is always active" and "the active track was deleted" need no reconciliation effect. Deliberately not persisted (a track id means nothing across projects). It drives stave coloring, which track the piano roll shows, and the piano-roll keyboard highlight.
- **Notation and a piano keyboard are shown together**, not switched between (there is no `view` mode). The keyboard is a full-width collapsible panel **below** the transport in `AppLayout` — it is the only row down there whose height changes, so with it in between, collapsing it moved the transport, which is the row a hand goes to without looking; fixed rows first, the variable one last. **It starts expanded, and the collapsed state is a device pref** (`store.keyboardCollapsed`, persisted by `bindDevicePrefs` in `App.tsx`, which also owns theme, developer mode, pitch display and font size). **Collapsed it renders nothing at all**, because the show/hide control is the transport bar's rightmost button rather than a header row of the keyboard's own: that row cost a whole strip to hold one button, and it put the control that _reveals_ the keyboard inside the thing it reveals, so it had to survive collapsing in order to stay reachable. The label it also carried — the active track's instrument and name — went with it; the canvas gutter already paints both beside every system, and `trackInstrumentLabel`'s drum-kit rule is tested where it lives, in music_types. The rest of the panel: keys in true physical layout (`keyboard-geometry.ts` — whites tile, blacks straddle the boundary between them, whites emitted first so blacks draw on top), lighting the active track's sounding pitches via music_drawing's `playingPitchesForTrack`. **Its keys, range, naming and label gutter come from music_drawing's `keyboardKeys`, the colours from `keyboardKeyFill`, and the lit set from music_drawing's `litKeys` fed by `usePlayingPitches` (memoised on the pitches, so the set changes identity only when the keys do — the Profiler test pins it). Out-of-range **black** keys dim too (`KEYBOARD_OUT_OF_RANGE_BLACK`). **Its range is the active track's instrument**, not always all 88: `gmInstrumentRange` in music_lib is a curated table (family default, per-program overrides where the default would be badly wrong), and `snapToWhiteKeys` widens it to whole keys because a black key at either end has no white neighbour to hang off. **It widens further to reach every note the track holds** (`trackKeyboardSpan` in music_drawing, shared with the native app — past A0 and C8 if need be), because an import can hold notes the instrument cannot play and a keyboard stopped at the compass lit nothing for them. Keys outside the compass are `outOfRange`: white ones are drawn `KEYBOARD_OUT_OF_RANGE_WHITE`, and none of them sounds or writes — the drawn key ignores the press and `pressKey` ignores a MIDI keyboard's. The same compass decides the notation's orange `noteOutOfRange` colour (the note set is music_types' `outOfRangeNoteIds`, a pure helper, read by both the notation and the inspector) and every editing refusal (`range-refusal.ts` in music_editing: entry, transpose, accidentals, the inspector's pitch, pitch drag, moving notes to another part, and pasting onto another part). Changing an existing note is allowed when it moves _toward_ the range, so an imported low note can be fixed a step at a time; a paste back onto the part the notes came from is not checked, so a cut and paste along one part cannot lose them. It follows a track change and an instrument change alike, since both move `midiProgram`. Keys are labelled at **C and F** — the landmarks of the black-key groups, so no white key is more than two steps from a reference without labelling all seven per octave. **It is also an input device**: pressing a key auditions it through `playbackController.noteOn/noteOff` on the voice `auditionVoiceFor(track)` names (music_types, shared with the native keyboard; it resolves a percussion address to the kit playback uses) (which touch no transport state — no caret move, no play/pause change, no active-note highlighting), and releasing writes a note at the caret whose duration is the tap's length, snapped by `durationForTap` to something the duration toolbar could also have produced. The caret then advances past what was written, so a run of taps lays out a melody instead of overwriting one position. Tap length is matched on a _ratio_, not a difference: 40ms over is nothing against a whole note and everything against a thirty-second. The DAW-style piano-roll timeline it replaced is gone, and with it mouse note-dragging and voice reassignment — see `docs/superpowers/specs/2026-07-27-piano-keyboard-view-design.md`.
- **The engine is handed a plan, never a score — and that rule now lives one level down.** `IMusicPlayer.load(score)` is the public surface: `@sudobility/music_player` owns `playbackPlan`, so the app hands over a `Score` and the player builds the plan. Inside that package the `PlaybackEngine` interface still takes a `PlaybackPlan` and does no score maths, which is where the rule was always actually about. A mix change while playing still calls `applyMix(tracks)` — tracks only, so changing a gain does not rebuild every note.
- **Playback goes through music_lib's adapter, and the sound lives in music_player.** `playbackController` (aliased `playbackAdapter`) binds the store to `IMusicPlayer`: it owns the score subscription, the caret, the selection and the store writes; the player owns the engines, the plan and the performance↔score tick translation. `getMusicPlayer()` comes from the player's own singleton — `initializeMusicPlatform` and music_lib's platform registry are gone.
- **`@sudobility/music_player` must stay out of Vite's dep pre-bundling.** Its web entry lazily `import('js-synthesizer')`, and esbuild's pre-bundler resolves that eagerly into a chunk whose worklet asset URLs no longer point where the app serves them. The symptom is a blank page with no console error while `bun run build` succeeds — it cost a full e2e run to find. It sits beside `music_lib` and `music_io` in `optimizeDeps.exclude`.
- **`SOUNDFONT_ASSETS` is shared between playback and export on purpose.** Audio export renders through the same soundfont as playback, so the file is a recording of what was heard; two sets of URLs would become two fonts the first time one was updated. The app orchestrates the halves — `renderEvents` + `renderSamples` from music_player produce PCM, `io.audioCodec` encodes it and `io.fileExporter` writes it — so neither platform package depends on the other.
- **Playback must not touch the main thread more than it has to.** A notation redraw rebuilds and re-formats every VexFlow object in the window (~5ms), and Tone.js schedules on that same thread, so colour repaints are coalesced to one animation frame and skipped when nothing _visible_ changed — `ScoreCanvas` in music_drawing does both now. A change of lit notes redraws **one track**: `web-canvas-surface.ts` paints through `createLayeredPaint`, keeping everything but the active track's notes on an offscreen canvas until something other than the lit notes changes, and the canvas `prepare`s the window following playback will scroll to a column per task, so a system break only paints. Measured on a dense eleven-track import in Chromium: median repaint 1.4ms → 0.6ms, frames over 25ms during 30s of playback 22 → 6 and 18 → 1. The keyboard reads `usePlayingPitches`, which keeps one set until a key of the active track changes, so another part's notes render nothing (`PianoKeyboardView.test.tsx` pins it with a `Profiler`). `positionTick` (30Hz) never reaches `ScoreEditorView`'s top level: the playback binding reads the shared position and talks to the canvas directly. Both have regression tests; don't undo either without re-measuring.
- **A drag on the Unplugged stage is a score command per frame, and three things used to make each one expensive here.** `AppLayout` subscribed to the whole `score` and to `validationIssues` to derive nothing but `disabled` flags, so every command — every frame of a walk or a drag — rendered the entire editor chrome, dialogs included; it reads `hasScore` now and the issue navigator takes the score from `getState()`. `bind-player` reloaded the player on every new score identity, and while _stopped_ `player.load` rebuilds the whole note schedule; a change that touched `score.unplugged` and nothing else (`onlyUnpluggedChanged`, identity per field) now pushes `applyMix` instead, the same thing the player itself does for a mix change while playing, and `bind-player.test.ts` pins that a listener move never calls `load`. The third — two `JSON.stringify` and a validation walk per command inside music_editing — is fixed there and documented in its CLAUDE.md. The native app's `bind-player.ts` mirrors the first two, since the "initial lag" on a map drag was reported on both platforms.
- **The transport does not say "playing" until a note can sound.** The first press of Play has a 23MB soundfont to fetch and hand to fluidsynth — seconds — and the engine used to report `playing` immediately so the button would not look dead. That made the caret lie: it interpolates from elapsed real time between position reports (below), and _no reports arrive during the load_, so it glided silently through several bars and snapped back when the music finally started at the beginning. `SoundfontPlaybackEngine.play()` now reports only once the synth is up (synchronously when it already is, which is every press after the first), and `PlaybackLoadState` carries the wait: `SynthLoadIndicator` shows "Preparing instruments 45%" and `PlayPauseButton` — its own subscriber, since the load reports per percent — goes disabled and busy. Two separately-sound optimisations that could not both be right; the indicator is what makes honest reporting affordable. e2e presses Play through `startPlayback()`, which waits on a load-sized budget rather than Playwright's default five seconds.
- **The canvas, the cursor and hit-testing are one shared interface: `ScoreCanvas`** (`music_drawing/docs/score-canvas.md`, with numbered expectations and tests). The web and native editors used to wire these separately and disagreed — about units, about zoom, about where tick 0 sits and whether the caret hides under the gutter. Now neither app computes canvas geometry: `ScoreEditorView` feeds a `ScoreCanvas` (score, view, scroll, active track, selection) and asks it `hitTest`/`tickAt`/`noteIdsInRect`/`contentSize`; `web-canvas-surface.ts` only paints and moves the caret `<div>`. **The cursor is described, not written per frame**: `bindPlaybackToCanvas` hands the canvas a motion (tick, time, rate) and re-describes it only on drift, and the surface replays it with `cursorTickAt`/`cursorXAt` in a `requestAnimationFrame` loop, writing a `transform` (never `left`/`top`). The binding decides once per burst of notifications (`defer: queueMicrotask`), because a stop homes to 0 and then reports stopped in one call — decided per notification, that read as a jump to bar 1 and scrolled the page there. **The page turn rides the cursor's own clock**: `subscribeCursorSystem` announces a system crossing when the canvas swaps the path, and the binding follows on that rather than on the next 30Hz position report — the caret is placed in content coordinates, so a follow scroll that lands late leaves it clipped outside the viewport, which is what it did here at every wrap (about half the duration measured on the Mac, only because this repaint is faster). `followTo`'s once-per-bar `followedMeasure` guard is what stops the report arriving afterwards from following the same bar twice.
- **Nothing high-frequency may be read at a large component's top level.** `positionTick` arrives 30x/sec and `selectCurrentMeasureBeat` returns a fresh object each time, so reading either high up re-renders that whole subtree 30x/sec — profiling playback showed `AppLayout` (and through it the notation and keyboard) plus the whole `TransportBar` of forwardRef controls doing exactly that, 124 renders in 4s. Each position-driven readout is now its own subscriber component: `StatusPosition`, `MeasureBeatReadout`, `PositionScrubber`, `Timecode`; the caret is not a React subscriber at all. Same rule for `activeNoteIds`. Keep new readouts isolated.
- **The app owns the platform library.** `music_io` declares its audio engine an _optional_ peer, so nothing installs it for you — this app adds **`js-synthesizer`** (libfluidsynth compiled to WASM, driven from an AudioWorklet), and a React Native app would add its own engine instead. That is the point of the split: a fresh `bun install` fails loudly with `Cannot find package` rather than silently shipping the wrong platform's audio. It was `tone` until the soundfont engine replaced the synthesised approximations; `tone` is now imported by nothing in music_app, music_lib or music_io and has been removed from this package's dependencies.
- **Platform services come from `getAppServices().io`**, never from `music_lib` directly: `fileExporter` for the three export handlers (which are `async` now — saving is asynchronous on React Native, which writes a file and opens a share sheet), `xmlParser` and `midiCodec` for the import dialogs and the benchmark. Component tests that render `AppLayout` or either import dialog need `installTestAppServices()`, because those dialogs build their service at render and `AppLayout` mounts them even while closed; `resetTestAppServices()` clears the platform registry too, so a suite cannot leak one into the next.
- **On a percussion track, `midiProgram` is a drum kit, not an instrument** (`gm-kit.ts` in music_lib). General MIDI selects the kit with a program change on the drum channel, so the same field that names a violin on a pitched track names Brush on a drum one — and the two never agree, because Brush is 40 and program 40 is Violin. Every program-keyed table (`gm-range`, `gm-polyphony`, `gm-transposition`, `gm-icon`) therefore answers for the wrong thing on a drum track unless it goes through **`track-instrument.ts`**, which takes a `Track` and is the one place the distinction lives: `trackKeyboardRange`, `trackMaxPolyphony`, `trackWrittenTransposition`, `trackInstrumentIcon`, `trackInstrumentLabel`, `soundingPitchForTrack`. All three wrong answers shipped — the toolbar refused a three-piece drum hit (Violin plays two notes), written mode drew a TR-808 part an octave off (kits 24-25 are guitar programs), and the keyboard offered a piano's compass. Only the eight addresses GM defines are kits, so a score can arrive at one that is not: `gmKitAt` resolves any address to the kit whose region contains it, `setScore` corrects percussion tracks **inbound** (before the store adopts the score, so opening a project never marks it dirty), and `changeClefCommand` re-resolves when a track crosses into or out of percussion. The keyboard labels every drum key, blacks included — Closed Hi-Hat is F♯ — on two staggered label rows, since a black key's label would otherwise land on both its neighbours'.
- **Instruments are the 128 General MIDI programs** (`gm.ts` in music_lib). `Track.midiProgram` is the identity; `instrumentName` is set from the catalogue alongside it so the two cannot drift. Icons are single-colour line art, authored once in music_lib (`icon-art.ts` shapes + `gm-icon.ts` table) and replayed by two renderers: `icon-canvas.ts` strokes them into the canvas track gutter, `instrument-icon.tsx` emits the same shapes as `<svg>` with `stroke="currentColor"`. That shared colour is the point — emoji kept their own and stayed bright beside a dimmed inactive track name. Paths are authored in a deliberately small SVG subset (absolute `M`/`L`/`C`/`Q`/`Z`, plus explicit circles) parsed by `parseIconPath`, because the canvas alternative is `Path2D`, which jsdom lacks — the gutter's drawing would be untestable. Anything outside the subset throws. Every GM family has its own synthesized voice (sixteen categories; only guitar/ethnic and the two FX families share, since those timbres are the same shape). They are approximations, not samples — brass is a filtered sawtooth, recognisably brass-shaped rather than actually a trumpet. `createPianoInstrument`'s `Tone.Sampler` branch is the structured route to real fidelity if samples are ever bundled.
- **Every import and export is one call on `music_io`.** `io.openMidi`,
  `io.analyzeMidi`, `io.openTracker`, `io.openMusicXml`, `io.saveMidi`,
  `io.saveTracker`, `io.saveMusicXml`, `io.saveAudio`. The app no longer pairs a
  codec call with a `fileExporter.save` — that pairing is what made `AppLayout`
  grow four near-identical export handlers, and it moved to music_io with the
  file layer. `xmlParser` has left this app's field of view entirely as a
  result: still a capability, but only music_io uses it. The export menu is
  built from music_types' `WRITABLE_EXPORT_FORMATS` and every entry goes
  through one `handleExport` over music_lib's `planExport` and `exportFilename` (the title
  kept, reserved characters replaced). The **project file** is the one export
  that is not a codec call: it writes music_codecs' `serializeProjectFile` as
  `<title>.moo` — the extension is the plan's, since `WRITABLE_EXPORT_FORMATS`
  says `moo` itself now rather than the app overriding a `json` — the same
  document the native app keeps locally, and audio
  renders through `renderScoreAudio`.
- **Two exceptions, both deliberate.** `saveTracker` takes a `TrackerModule`
  rather than a `Score`, because the fit report has to be shown _before_
  writing — a clean fit costs no extra click, anything lost shows the numbers
  first — so the app still runs `scoreToTracker` itself. And `saveAudio` takes
  PCM, because rendering is a live synth in `music_player` while a codec is a
  pure function music_io may call; the app renders, then hands the samples over,
  which is why neither platform package depends on the other.
- **Every import lives on the dashboard, because every import makes a project.** MIDI, MusicXML, Audio, `.MOD` and a project file (`.moo`, and the older `.moosiac`/`.json`, all read by music_codecs' `parseProjectFile`) all end in `newProject(...)` followed by a navigation, so an Import menu on the editor's own title bar could only throw you out of the project you had open — it was removed. **That includes opening a `.moo`**: the editor has no Open of its own, because opening one makes a project; the dashboard's Import project file accepts all three extensions, and `DashboardPage.test.tsx` pins that. The one exception is audio-as-a-_track_, which writes a transcription onto the open score: that is a track operation, so it lives under the editor toolbar's **Add Track** select ("Track from Audio…"), not under an import menu. The dashboard's Import Audio is the other half of the same feature and builds a whole project instead, which is why it has to size its own empty score — `addTranscribedTrackCommand` copies the measure grid of an existing track and silently drops notes past the last bar, so the placeholder track it copies from is created long enough and then deleted.
- **A recording opens as soon as it is uploaded, and its parts arrive in the score.** Import Audio used to leave you on the dashboard with a `transcribing` card that refused to open, on the grounds that a transcription had nothing to show for minutes. It has now: `midi_transcriber_api` reports each stage as it starts with a preview of everything transcribed before it, `music_api`'s `settleTranscription` writes each preview to the project as its score (still `transcribing`), and the project's live socket sends it on as a fresh `snapshot` plus a `progress` naming the part being worked on. So `handleAudioImport` navigates to the project exactly as a generation does, a `transcribing` card opens like any other, and the editor needs nothing new — `useProjectGeneration` already treated both statuses as busy. **A preview is a whole score, not a fragment**: a generation writes bars into a grid that already exists, where each preview re-derives tempo and bar count from the notes so far, so there is no range to replace. `GenerationStatusStrip` takes `status` for the sentence alone; the lock, the stream and Cancel are the same. Previews reach the editor **only over the socket** — the polling fallback still shows the result at the end — and a transcription that fails is toasted from `AppLayout`, because it has no job for the hook's own failure toast to read.
- **Bar-level UI sizing is stated, not inherited.** Buttons, Radix select triggers and file-picker `<label>`s each size themselves from their own content — an 18px glyph with `p-1.5`, `text-sm` with `py-1`, whatever padding a label was handed — so a toolbar row of them comes out ragged no matter how the padding is tuned. `CONTROL_HEIGHT_CLASS`/`ICON_CONTROL_CLASS`/`TEXT_CONTROL_CLASS` in `notation-icons.tsx` state the height once for both editor bars (h-8), and `ROW_CONTROL_CLASS` in `DashboardPage` does the same for the page toolbar (h-10). They live beside `ICON_GLYPH_CLASS` for the reason that does: importing them from a toolbar drags that module's dependency graph into the others and broke the app at start-up once. **Title-bar tooltips must pass `placement="bottom"`** — the bar is at the top of the window, so the default upward bubble is clipped by the viewport.
- **Track info is drawn in the canvas, not the DOM.** `layout.ts` reserves `TRACK_INFO_WIDTH` (220px) at the left of every system and `drawTrackInfoGutter` paints each track's name, instrument and mute/solo there, repeating per system. Alignment is structural — same coordinate space as the staves — which is the point: two earlier attempts at a DOM list positioned from reported geometry both shipped scrolling independently of the sheet they mirrored. Don't reintroduce one.
- The gutter is **pinned to the viewport's left edge**, not content x=0, or it would scroll out of view in continuous mode. So `trackIdAtGutterPoint` hit-tests in **viewport** coordinates while every other editor hit test uses content coordinates — the one place they differ. Anything in the DOM above the canvas has to opt out of that band itself: the caret is an abspos child of the scroll box, so it scrolls with the content and would slide _over_ the track info — the web surface hides it while `cursorVisible` says its view x is inside the gutter, reading `scrollLeft` before it writes any style so the check cannot force a synchronous layout in the playback frame loop. The gutter `clearRect`s its region rather than filling it, so its background is the surface behind the canvas — the same one the sheet sits on, matching by construction. (`RenderTheme.background` existed briefly for a fill and was removed; don't reintroduce it.) The instrument glyph comes from `gm-icon.ts` in music_lib, which is why the table lives beside the catalogue rather than in the app.
- **Track editing lives in the property sheet, and the rules live in music_lib.** There used to be two track editors — a panel beside the keyboard and the inspector's Track tab — which is how they disagreed about whether program 0 was "Piano" or "Acoustic Grand Piano". There is now one, the inspector's Track tab, and it is first because it is the only tab that always has something to show (there is always an active track; the note and measure tabs are an empty state until you select something). It **reflects and invokes only**: the track comes from `selectSelectedTrack` and every edit is a `track-slice` action (`renameTrack`, `setTrackInstrument`, `setTrackClef`, `setTrackMix`, `removeTrack`, `canDeleteTrack`). The rules those enforce are rules about a score, not about a panel, which is why they are in music_lib — `setTrackInstrument` takes the **catalogue value string**, kit prefix and all, so the kit/melodic distinction is resolved in one place rather than at each call site; it carries the existing notes into the new instrument's compass by whole octaves (`instrument-fit.ts`), and reports `outOfRange` rather than half-applying when the part is wider than the instrument can play. The panel supplies the sentence for that. The name field is a draft committed on blur, or every keystroke is its own undo entry. Content controls go `disabled` while the transport plays; volume, pan, mute and solo stay live, because mixing is not editing.
- **Generation is a server-side job, and the project's status is the source of truth.** `POST /jobs` returns as soon as the row exists; `music_api` runs the work in-process, applies the result to the project itself, and flips `projects.status` back to `ready`. The editor polls `GET /projects/:id/status` — status only, because the score cannot change while generating and shipping it every 3s was enough to time jobs out under load. `generating` means "still wanted": cancel just writes `ready`, and the running job discards its result when it next looks (including between chunks of a long one). Writes to a generating project are rejected with 409 `PROJECT_GENERATING` — that is what makes auto-apply sound, since the job's request was built against the stored score. `music_api` therefore depends on `@sudobility/music_lib` for `replaceRegionCommand`; a `ScoreCommand`'s `execute` is a pure `(Score) => Score`, so it applies with no store. Orphaned `running` jobs are failed at boot, or their projects would be uneditable forever.
- **The editor watches the _project_, not its own job** (`useGenerationJob.ts`). A generation started on the dashboard belongs to no job id in the editor, so a job-only poll left it showing the placeholder score with no overlay and no reload. It also reloads on a change in `updatedAt` rather than on having _witnessed_ the transition: open a project in the instant its job finishes and the change happens between the fetch and the first poll. The reload is awaited **before** the overlay clears, or the editor shows pre-job music as though it were the result.
- **One candidate, always.** Requests pin `candidateCount: 1` and the result is applied; there is no candidate list, no A/B compare, no accept step. This follows from the job model — when a job lands, nobody is looking. `CandidateList`, `preview.ts`, `RegenerationPanel` and `previewFragment` were deleted with it; `RegenerateRegionResult.candidates` survives as the wire format carrying one entry.
- **Replace Notes is the one region deliberately _not_ snapped to measures.** `replacementRegion` in `music_lib` derives the tick range per scope; `prepareRegenerationRequest` snaps its selection to full measures, and `prepareRegenerationRequestForRange` does not — Replace Notes needs the latter. A non-contiguous selection is replaced as its bounding span, and the modal says how many notes inside it were never selected. `preserveMeasureCount` is omitted for a sub-measure region, where it means nothing.
- **Tracker import is one step, not a wizard** (Import → Module), and accepts **`.mod`, `.dsm`, `.s3m`, `.xm`, `.it` and `.mptm`** — chosen by magic bytes rather than by file extension, so a mis-named module still imports and an unrecognised file fails naming what it found. A tracker module states every note and instrument outright, so unlike MIDI or audio there is nothing to estimate and nothing to confirm. Bytes are decoded by `io.modCodec` (one shared implementation across all three platforms — nothing about it is platform-bound; the capability exists so every format is reached the same way), and `trackerToScore` in music_lib turns the decoded module into a score. The model it works on is **format-neutral** (`TrackerModule` in music_types): cells carry MIDI note numbers rather than Amiga periods, patterns carry their own row count, and speed/tempo arrive already normalised — so the score mapping has no format branches and the other tracker formats are decoder work only. **Notes are grouped by instrument, not by channel**, so all the bass lands on one track wherever it was played from; two channels using one instrument at the same moment become separate voices in the same measure. The order list is flattened — a pattern played three times becomes three sets of measures — because a score has no concept of "repeat this pattern" — and a `Dxx` pattern break now ends its pattern there, which it did not before: ignoring it imported a module with too many bars, silently. **Every voice is filled with rests** (`fill.ts`), because a bar that does not add up renders short: the importer used to place notes and nothing else, which produced 554 `measure-underfull` warnings on a real module. **Export writes notes only** (`scoreToTracker` in music_lib → `modCodec.encode` in music_io). No sample data: a module is a notes format under the notes/audio split, so its instrument slots are named after the track's instrument and left empty, and the file is silent until a tracker user fills them — the export dialog says so. Three things are lossy and all three are counted into a `TrackerFitReport` rather than hidden: the row grid (a row is a sixteenth, so anything shorter is dropped), the channel count (the sum of each track's widest voice count, capped per format), and the note range (MOD's three octaves are MIDI 36-71, anchored on `period.ts`'s reference period so import and export agree — every limit in `limits.ts` is anchored to our own decoder rather than to the spec, because the two only have to agree with each other). Out-of-range notes move by whole **octaves**, not to the boundary: an octave displacement keeps the pitch class, so a bassline still reads as that bassline. A clean fit writes with no extra click; anything lost shows the numbers first. Scope is chosen **before** the fit is computed, because exporting visible tracks only may bring a score within a channel limit all tracks exceed. Tempo is written **into cells as well as the header**: `TrackerModule` carries no initial-speed field and `tempoChanges` reads only cells, so a header-only tempo round-trips back as 125 BPM. XM's `F` splits speed from BPM at `0x20`, which is exactly where `speedAndTempoFor` already divides them (speeds 3/6/12, tempos 32-255) — but one cell cannot hold both, so they take two channels. **DSM and MPTM are import-only** — nothing reads DSM that does not read a better format, and OpenMPT reads IT natively. Only XM is written so far; `encode` throws by name for the rest. **Known limitation:** `periodToMidi` computes from a reference period rather than ProTracker's table, which finetune shifts, so a real module can land a note or two differently than a tracker would show. It lives in music_io beside the MOD reader, because MOD is the only format that has periods at all.
- **IT/MPTM are one reader** (`it.ts`); MPTM is IT with `cmwt == 0x0888`. Do **not** discriminate on the `OMPT` marker at offset 60 — it means "written by OpenMPT", and an ordinary IT can carry it. Two things about this format are silent if you get them wrong. **Its pattern encoding is stateful**: a mask bit in 1/2/4/8 _reads_ a field, and one in 16/32/64/128 _replays_ the channel's remembered value and **consumes no bytes** — so a reader that drops the replay half still unpacks every pattern to its exact declared row count consuming its exact declared bytes, passes every structural check, and silently loses a quarter of the notes with almost all instrument assignments falling back to 0 and grouping onto one wrong track. There are two independent per-channel memories: the last _mask_ (for a channel byte with bit 7 clear, which is the common case) and the last _value_ per field. **And the note base is 0**, deliberately unlike XM/DSM's 11 and S3M's 12: IT note 60 _is_ MIDI 60, because IT displays middle C as "C-5" where scientific notation says C4 — a naming difference, not a pitch one. IT's full 0-119 range only fits MIDI at base 0. Anything ≥ 253 ends the note: 255 off, 254 cut and **253 fade**, an OpenMPT extension present in the MPTM fixtures and in none of the four ITs measured — reading it as a pitch emits MIDI 253. Both rules are pinned by tests against `thereal1.it` and `preparator.mptm`; the fade was caught by the acceptance suite's generic MIDI-range assertion, not by design.
- **Printing is `music_drawing`'s, and it is monochrome now.** `print-layout.ts` moved out of this app into the library so the native app prints from the same decisions: page mode, `PRINT_WIDTH`, `PRINT_SCALE`, no gutter, no editing state, and `printSystems` slicing each system from its measure-number band rather than its top stave line. `PrintView` asks `printPlan` for the whole plan — scope, part extraction, `displayScore` (so a note under an `8va` prints where it is written, not an octave high as it used to), page turns and empty-page dropping — and offers music_types' `PAPER_OPTIONS`/`ORIENTATION_OPTIONS` (vocabulary, so not music_drawing's). One thing changed in the move — print used to use `LIGHT_RENDER_THEME` (notes at `#3f3f46`), and now uses `DEFAULT_PRINT_RENDER_THEME`, which is `PRINT_INK` throughout. The reason is that a printed part has no active track, no selection and no playhead, so every state colour on paper is a colour that means nothing to the reader, and on a monochrome printer a #3f3f46 note is a grey one among black ones. If a grey score was wanted, pass a theme: `printRenderOptions(trackIds, LIGHT_RENDER_THEME)`.

- **Cut, copy, paste, clear and delete live on the score's context menu, not on the editing bar.** They were four toolbar buttons, and all four share a problem a bar cannot fix: they act on something already selected, and they cannot say _what_. Delete means three different edits — a track goes, a bar goes and the score renumbers, notes go and the ones behind shift forward — so a permanently visible "Delete" is a control you have to try in order to understand. `ScoreContextMenu` (right-click) and music_app_rn's `ScoreActionsSheet` (long-press) both open **on the object** and name it first: a small grey "Track" / "Bars" / "Notes" above the entries, from `selectionKind`. Cmd+C/X/V are unchanged.
- **A context click selects what is under it, then opens** — same hit-test order as an ordinary click (track gutter, then measure gutter, then a note), because a menu that opens over one thing and acts on another is the one failure this shape must not have. Both halves are music_editing's: `selectForContextMenu` picks the target and `scoreContextMenuModel`/`runScoreContextAction` build and run the entries, so `ScoreContextMenu` only draws a model. **A click inside an existing selection keeps it**: right-clicking one of four selected bars means those four, and narrowing to the clicked object is the classic way a context menu throws away the selection somebody just built.
- **Clear and Delete are different edits, and the difference is what survives.** Clear keeps the container and empties it — a cleared bar keeps its number, signatures, barline, repeats and clef change, a cleared track keeps its instrument, clef and mix. Delete removes the container and everything behind it moves up. Before this only Delete existed at each level, so "empty these four bars" meant deleting them and adding four back, which loses every marking on them and renumbers the score twice. `clearMeasuresCommand`/`clearTrackCommand` are in music_types and **spread the measure** rather than rebuilding it, so a field this feature has never heard of survives a clear; rebuilding from known fields is how a clear comes to silently drop a marking added later. For notes there is no container, so Clear _is_ delete-without-closing-the-gap.
- **The clipboard is tagged, and Paste is offered only on a matching kind.** `ClipboardData` is a union of `notes` / `measures` / `track`; it was a bare `{events, anchorTick}` while notes were the only thing copyable. **A measures entry is a vertical slice** — the bars at those indices across _every_ track — because a bar is the same bar on every stave and `deleteMeasureCommand` already worked that way; a slice that held one part's bars would paste back leaving the staves disagreeing about where bar 40 is. `canPasteInto` gates the _menu_; `paste()` itself is deliberately laxer for notes, because copying a phrase, clicking into another part (which moves the caret and selects nothing) and pressing Cmd+V is the ordinary way to use it, and enforcing a menu's rule there would break the keyboard.
- **Paste asks insert-or-replace only when the two would differ**, per kind: inserting bars lengthens the score and replacing them does not, and the same holds for a track, so those always ask; notes are the one case where the answers can coincide (pasting into empty bars pushes nothing and overwrites nothing), which is what `pasteNeedsPrompt` tests. **Cut keeps asking too** — it is copy plus a removal, and which removal is exactly the Clear/Delete question.
- **A pasted bar arrives whole; a pasted track adopts the score's grid.** A bar brings its own notes, signatures and length, and every track receives the same column, so the grid stays consistent. A track is fitted to the destination's bars instead — a part copied from a longer score must not silently change how long every other part is, because adding bars is `insertMeasuresCommand`'s job. Both inversions are pinned by tests in `clipboard-commands.test.ts`, and the one that shipped broken was re-timing: `adoptMeasure` leaves the source's `startTick` on the measure _and_ its events so the two agree, and lets `rebuildMeasureTicks` shift the pair — stamping the destination's tick on the measure alone leaves every pasted note outside the bar that holds it, which looks like an empty bar rather than an error.

- **Every modal is `FormModal`** from `@sudobility/components` — there is no bare `Dialog` left in this repo, and a new dialog should not reintroduce one. `FormModal` is full-screen on a phone and a centred dialog above `sm`, and it owns three things the body must therefore _not_ repeat: the title (a heading in `children` prints it twice), the dialog's accessible name (it labels itself from `title`, so no inner `role="dialog"` wrapper is needed to be findable by name), and the scrolling of the content area. Footers come from `actions` — an ordered list where the last entry defaults to primary and the rest to ghost; `actions={[]}` means no bottom bar at all (`ShortcutHelpDialog`, `DeveloperSettingsDialog`, whose settings apply on change). The plain `onSave`/`saveLabel` shorthand renders one full-width CTA and cannot be destructive, which is why `ConfirmDialog` uses `actions` instead. **Any dialog whose footer has a Cancel must set `closeAriaLabel` to something else** (`"Close dialog"` here): the top-bar × is named `"Cancel"` by default, and two controls with one accessible name are ambiguous aloud and a strict-mode failure in tests.
- **`@sudobility/consumables_client` is inlined in `vite.config.ts`'s `test.server.deps`,** for the same reason `music_lib` is: Node's ESM loader is stricter than what these packages are built for. It is compiled by `tsc` with extensionless relative imports — the house style it shares with `entity_client` — which Node rejects as `ERR_UNSUPPORTED_DIR_IMPORT`. The browser never sees it, because Vite resolves it; only vitest does, since it hands bare dependencies to Node. Don't add `.js` extensions upstream to "fix" it — that would make it the one package in the family built differently from the rest. `consumables_pages` needs no entry: it is Vite-bundled like `entity_pages`, so its output has no relative imports at all.
- **`ConsumablesApiClient` carries no token; its `NetworkClient` must.** `MusicClient` takes a token per call, so `FetchNetworkClient` deliberately adds no auth — but the consumables client has no token parameter at all and expects an already-authenticated client. It therefore gets `AuthenticatedNetworkClient`, a wrapper in `config/initialize.ts` that attaches the bearer per request (read per request, never captured: a token held from construction starts failing an hour into a session). This is still the one `fetch()` call site; only the headers differ. Every unit test mocks the hooks, so nothing but the e2e catches its absence — it surfaced as "Authorization header required" rendered inside the store page. **And the token must wait for Firebase to restore the session**: `auth.currentUser` is `null` between `getAuth()` and the first `onAuthStateChanged`, so reading it straight away answered `null` for a signed-in user, the wrapper omitted the header entirely, and the server said 401 "Authorization header required" — no header at all, rather than a rejected one, which is the tell. `readFirebaseToken` awaits `authStateReady()` first; it resolves immediately after start-up, so this costs nothing. Anything that fetches on mount could lose that race; the credits balance did.
- **Credits are quoted, not calculated.** The Generate dialog shows `durationMeasures × tracks.length` — one credit per bar **per instrument**, because a quartet costs about four times a solo of the same length to produce and that is what the server bills. It says "about": the server charges what the model actually produced, which agrees whenever generation returns the requested length and is otherwise smaller, so the quote is never exceeded. Generate is disabled at a balance of **≤ 0 only**, and deliberately _not_ when the estimate exceeds the balance — a job may overdraw once by design, and a stricter rule here would refuse work `POST /jobs` would have accepted. The 402 still has to be handled: this check is a courtesy, and a user whose credits ran out in another tab reaches it. A refused job also **deletes the project it just created** — that project exists only to hold the generation, and without this a user with no credits collects an empty "Generated score" row on every attempt. `CreditBadge` is its own subscriber for the same reason every position readout is: a balance change must not re-render the notation canvas. It hides only when the balance is unknown, never merely while refetching, or it would flicker out of the bar. **A 402 opens the store, not a toast.** `POST /jobs` answers 402 `INSUFFICIENT_CREDITS` at a balance of zero; `music_client` maps that (and a bare 402) to `InsufficientCreditsError`, and `reportGenerationError` turns it into `dialogs.paywall` rather than an error message — it is the one API refusal with an obvious remedy, and it reads as a network failure otherwise. The dialog itself is `CreditPaywallDialog` in `@sudobility/consumables_pages` — presentational, fed labels and payment data, since every product that sells credits hits this same moment; `PaywallDialog` here is only the adapter, and is mounted once above the routes because a refusal can come from the dashboard or from inside the editor. Both it and the Credits page take their data and copy from `useCreditStore`, so the two cannot disagree about what a credit costs. **It is the one modal in this repo that is not `FormModal`**: `consumables_pages` depends on `@sudobility/design` alone, so the shared dialog hand-rolls its shell rather than dragging `@sudobility/components` into every consumer. It does not retry afterwards: the job was discarded and the project it would have filled was deleted with it. **A site administrator is never gated here**: `music_api` grants them free generation — no quota, no balance check, no charge — so they sit at a balance of zero forever, and this app's courtesy gate would refuse work the server would have accepted. `AuthProvider` builds one music_client hook context (`musicHookContext` in `config/initialize.ts`, token read per request) and takes `siteAdmin` from music_client's `useSiteAdmin`; `useMusicHookContext()` and `useSiteAdmin()` read them tolerantly (`false` with no provider, matching the closed default used while the request is in flight and when it fails), so a component that only wants to know whether to stand a paid gate aside needs no auth wiring in its tests.
- **`rsync`ing a local build into `node_modules` requires deleting `node_modules/.vite`.** Vite pre-bundles dependencies, so a freshly built `@sudobility/*` copied in during cross-repo work is ignored until that cache is cleared — the browser keeps running the old code while the file on disk is right. This cost two full debugging cycles: once a client method appeared to be missing, and once `getProjectStatus` returned a bare string so `const { status } = ...` was silently `undefined` and the generating overlay never appeared. Neither threw, so the poll's `catch` never fired. `music_lib` is already excluded from pre-bundling; everything else is not. **`bun run build` does not clean `dist`** either, so a file deleted from a lib's `src` lingers in the copy you rsync in — a stale `transcribe-service.js` survived the basic-pitch removal that way, and the deleted worker services did the same. Run `bun run clean && bun run build` before syncing. And any `bun add`/`bun remove` **in this repo** reinstalls `node_modules` from the registry, silently replacing every package you rsynced in — re-sync after one, or the next typecheck fails on a symbol you just added upstream.
- `vite.config.ts` sets `resolve.dedupe: ['react','react-dom','zustand']`. Normally redundant, but a local `bun link` of music_lib during cross-repo work exposes its dev-installed copies and two React instances break every hook — don't remove it.
- `vite.config.ts` excludes `@sudobility/music_lib` from dev-mode dep pre-bundling. This was originally for the lib's `new Worker(new URL(...))` calls, which esbuild's prebundler doesn't handle; those workers are gone (see music_lib's CLAUDE.md — the offload measured at 0.57ms of saved work), so the exclusion now only costs a slower cold dev start. Harmless to keep, and the `rsync`-a-local-build workflow above assumes it.
- **There is no worker anywhere in this stack.** A quantize of any size and a MIDI import both run synchronously. Don't reintroduce one without measuring first: `quantizeEvents` is 0.57ms at 2000 events and 9.53ms at 50,000, and `postMessage` structure-clones the event array both ways.
- **music_lib is told about its environment, never sniffs it.** `initializeApp()` calls `setErrorLogging(import.meta.env.DEV)`. The lib used to read `import.meta.env.DEV` itself, which broke React Native at parse time — `import.meta` is syntax, so a `typeof` guard cannot save it — and music_lib now has a guard test forbidding it outright. Anything else environment-shaped belongs here, not there.

### Network payloads

- **Reads return the score; writes return metadata about it.** `POST`/`PUT /projects/:id` and every snapshot write answer with `ProjectSaveResult`/`SnapshotSummary` — no `score`. The writer sent that score a moment ago and still holds it, so the echo was pure freight: it doubled the cost of creating a project and of every autosave. Don't "fix" a caller that seems to be missing `.score` on a write response by putting it back; take it from what you sent (`newProject` adopts the score it passed) or read the project.
- **The autosave omits the score when the score has not changed.** `project-slice` keeps the last-saved score by **identity** — every mutation goes through a command that returns a new object, so an unchanged reference is an unchanged score — and a save that exists only to persist `visibleTrackIds` or `zoom` sends `{name, uiPrefs}`. Hiding a track used to ship the whole score to record a list of ids.
- **`serverUpdatedAt` is how a client tells its own writes from somebody else's.** The store records where each read or write left the server; `useGenerationJob`'s poll reloads only when the reported stamp is **strictly newer** than that and no save is in flight. Before this the poll compared against its own last observation, so every autosave read as a foreign change and the editor re-downloaded the project it had just uploaded — resetting the undo history a few seconds after every edit. A write that goes around the autosaver (opening a snapshot, creating one — it re-parents the project row) must call `noteServerVersion`, or it reads as foreign too.
- **The poll's cadence follows what is happening**: `POLL_MS` (3s) while a job runs, `IDLE_POLL_MS` (30s) otherwise, nothing at all while `document.hidden`, and an immediate check on `visibilitychange`. An idle editor polling every three seconds forever was ~1,200 requests an hour per open tab to learn nothing; the visibility check is what makes the slow cadence unnoticeable.
- **Both directions are gzipped.** Responses by `compress()` in `music_api/src/index.ts`; requests by `MusicClient` itself, because a browser gzips responses it _receives_ automatically and bodies it _sends_ never — and uploading a score is what an autosave does on every debounce window. Bodies under 1KB go up as-is (gzip would only add a header), and the whole thing is gated on `CompressionStream`, which React Native's engine lacks. `decompressRequest` in `music_api` undoes it above every route, with a 32MB expansion cap because gzip amplifies ~1000× on the right input. Measured on a note-dense 64-bar four-track score: 490 KB → 37 KB (13×). Score JSON is the most compressible payload this system has.
- **Server-side work stays server-side.** Duplicating a project is `POST /projects/:id/duplicate`, not a GET followed by a POST; `parentSnapshotId` rides on `GET /projects/:id/status`, so nothing fetches a whole project to read one id. Queries that do not return a score select their columns explicitly (`META_COLUMNS`), because `db.select()` pulls every score JSONB out of Postgres for a list of names.

### Snapshots and publishing

- **Creating a snapshot flushes the live score first.** `createSnapshot` on the server copies the **projects row**, and autosave is debounced — so `AppLayout` hands `saveNow` to music_client's `useProjectSnapshots` as its `flush`, which runs before asking for a snapshot. Through the autosaver rather than a PUT of its own: `saveNow` is a no-op when nothing is dirty, where the direct write it replaced re-uploaded the whole score every time somebody took a second snapshot of untouched music. Delete that line and snapshots silently pin stale (or, right after generation, _empty_) music. The API integration tests cannot catch it — they snapshot a project created through the API, whose row is current by construction — so `AppLayout.test.tsx` pins it directly by editing inside the debounce window and asserting what the server held when `createSnapshot` ran.
- **Snapshot history is a tree, not a list.** Every snapshot has `parentId`; the live project carries `parentSnapshotId`. Opening v1 while v2 exists branches — v2 survives, and the next snapshot is v1's child. There is deliberately **no PATCH/PUT/DELETE route** on a snapshot: immutability is enforced by the absence of a route, not by a check somebody can forget, and a test asserts all three 404.
- **The URL names the language; the pref answers only a URL that does not.** Every route is `/:lang/…` so a shared link opens in the language it was shared in, and that stays authoritative. The `language` device pref (`store.language`, persisted by `bindDevicePrefs`) used to be stored and never read; it now decides where a bare `/` goes (`LocalizedHomeRedirect` → music_types' `preferredLanguage(pref, navigator.languages, SUPPORTED_LANGUAGES)`: the pref, else the device, else the first language the build ships, matched by language subtag). **The rule is shared and the list is this app's** — music_app_rn had its own copy that compared whole tags, so a reader with a stored `zh-Hans` was quietly given English; only `SUPPORTED_LANGUAGES` stays in `config/languages.ts`. The catch-all keeps a language the URL already has — `/zh/nope` lands on `/zh`. The redirect reads the pref from **storage**, not the store: `App` binds prefs from an effect, a parent's effect runs after its child's, and a cold `/` would redirect on the default. The pref is written only by an explicit switch (`useSwitchLanguage`, which takes the store through `ScreenContainer` and `useTopBarConfig`) — not on visiting a `/:lang` URL, or following someone's `/zh` link would decide what the reader's next bare visit opens in. The shared `LanguageValidator` still resolves an _unsupported_ `:lang` from i18next's own `language` key, which it owns.
- **The router sits above the auth gate.** `App.tsx` renders `BrowserRouter` with `/:lang/community` and `/:lang/p/:publicId` matched _before_ a catch-all whose element is `AuthGate`. Restructuring routing so the gate wraps everything again would silently make published links require a login. `music_api` mounts `/api/v1/public` **outside** `authMiddleware` for the same reason.
- **The public payload is built field by field** (`toPublished` in `music_api`), never spread from the row — so a column added to `snapshots` later cannot leak `user_id` or an email onto a public page. A test asserts the raw response body contains no `@`.
- **The e2e DB truncation needs `CASCADE`** now that `snapshots` references `projects`. Without it the `TRUNCATE` fails outright, every run inherits the previous run's projects, and it surfaces much later as a strict-mode violation on a duplicated project name in an unrelated spec.

### Audio and written pitch

- **Analysis lives in `music_lib`, codecs in `music_io`.** Pitch tracking (YIN), segmentation and tempo detection are pure functions over a `Float32Array` — testable with a synthesised tone and no browser. Decoding/encoding and `Tone.Offline` rendering need a real audio context and sit behind `AudioCodec`/`AudioRenderer` on `MusicIo`. `renderOffline` has **no unit test by design**: vitest has no `OfflineAudioContext`, so its only verification is the e2e round trip.
- **Import is monophonic, and the dialog says so.** One line at a time; chords and mixes are not attempted. Voice is not special — a vocal file takes the same path as a flute one.
- **Transcription emits unquantised ticks against the _detected_ tempo.** Correcting the tempo in the dialog rescales them; getting that backwards is silent, so the arithmetic has its own tests. Notes always land on a **new** track via `addTranscribedTrackCommand`, which is one command so an import is one undo step.
- **`writtenScore` is applied LAST in `displayScore`.** The pitch-drag preview splices in a _sounding_ pitch (it comes from the stored score, so the command it dispatches is right); transposing afterwards moves the dragged note with the rest of the staff. Applying the lens first draws that one note an instrument's transposition too low. `writtenScore` returns its input object unchanged in concert mode, so `computeLayout`'s identity cache is untouched unless the lens is on.
- **Sounding pitch survives written→sounding exactly; spelling does not.** Measured: 0 pitch changes and 567 spelling changes over 1323 combinations. That is why stored notes are never round-tripped through the display — display transforms one way, input the other way once, at entry.

### Drag to move notes

- **Option/Alt + drag moves; plain drag still pitch-drags.** The modifier is the whole disambiguation, which is why Option+press works on any note and selects it if needed — the **whole chord**, as a click does, and **only the selection**: the caret and the active track stay where they were, since a move is about which notes, like a box (`startPointerGesture`). Pitch is never changed by a move: vertical means _which track_, never _what pitch_.
- **The pointer handlers are memoized with deliberately narrow deps.** Anything read inside them that changes per-frame must go through a ref (`dropTargetRef` beside `dropTarget`, as `pitchDragRef` sits beside `pitchDragSteps`). Adding a branch that reads `layoutPlan` or state directly captures a stale value — this shipped as a bug once and only the e2e caught it.
- **The drop indicator never mutates the score.** A live note preview would splice into another track's measures and force a full relayout every frame.

- **New Project offers a singer, and it is the singer the arrangement is built around.** Turning **Generate for me** on prepends `DEFAULT_VOCAL_INSTRUMENT_VALUE` to the roster when there is no voice in it, and turning it off takes back **that entry by id** — a vocal the reader picked themselves is theirs, and the auto-added entry's id is carried in the draft itself — the whole form is `useReducer` over music_lib's `reduceNewProjectDraft`, shared with the native app, and the dialog only renders its selectors. `applyStyle` overwrites the whole roster deliberately, so it re-prepends afterwards: a vocal that vanished the moment a genre was chosen is a song the reader thought they had asked for. Removing it by hand forgets that id, so the toggle has nothing left to take back. Upstream, a voice sorts first in `rankTracksForGeneration` in every genre, which is what makes every other part accompany it.
- **`lyrics` is a switch, not an inference, and it is gated twice.** It shows only when `hasVocalInstrument` is true and defaults on, but `buildGenerateScoreRequest` drops the field unless the roster can actually sing — the server writes a lyric onto sung tracks and nothing else, so asking for words over an instrumental roster describes an outcome it cannot get, and gating it only in the dialog leaves a roster edited down to instruments still asking. It is not inferred from the roster alone because a voice program held as a wordless "ooh" pad is a different piece of music from a song.
- **The AI block clips its overflow only while it is collapsed.** `CollapsibleReveal` animates `grid-template-rows` from `0fr` to `1fr`, which needs `overflow-hidden` on the inner element — and that is what cut the Presets menu off at the bottom of the block, since the menu is an absolutely positioned child rather than a portalled one (which is why the Style and Mood selects were never affected). It is clipped while collapsed and through the 200ms transition, then not; dropping it immediately instead would let the full-height content overlap the rows below while the block grows. jsdom has no layout, so the test asserts the mechanism rather than the clipping.
- **The Prompt caption sits above the whole row.** It used to be inside the `<label>` wrapping the textarea, so the Presets button — which has no caption — started a caption's height _above_ the prompt box it belongs to. The caption is now above both, and the textarea's accessible name comes from `aria-label` rather than the wrapping label.

- **The preset briefs come from the server, and the button hides when they do not.** `useScorePresets(style)` replaces what was eight hardcoded prompts with no relation to the chosen genre — picking Reggae still offered a waltz. The server says _which_ briefs a style gets; `generateScore.preset.<key>` in the locale files says what they read, because the brief a reader picks is also the prompt sent to the model. The Presets control is **not rendered** at all unless a non-empty list has arrived: a button that opens an empty menu reads worse than no button, and one that is merely invisible is still in the tab order. `i18n.exists` filters what arrives, so a server one version ahead shows fewer briefs rather than printing an id at the reader. `preset-contract.test.ts` is what stops that silently: `locale-parity` cannot see a key missing from **both** locales, which is exactly what a new server brief is.
- **The default title follows the toggle, and is the placeholder as well as the fallback.** "New Score" blank, "Generated Score" generating — a placeholder showing a name you do not get is a label for a value that never existed. It reaches the _project name_ and the generation request; `buildNewProjectScore` still receives the raw title, so a blank field leaves the score's own metadata at "Untitled", which is what names an exported file. The score's title and the project's name are different things.
- **Component tests need `withQueryClient`.** `App.tsx` wraps everything in a `QueryClientProvider`, so any component that reaches the server through a hook has one in production — a test rendering it alone does not, and the failure is a thrown "No QueryClient set" that takes the whole render down rather than a missing value. `src/test/query.tsx` supplies one with retries off and no cache between tests. music_client's hooks build their own `MusicClient` from the services' `networkClient`, so `installTestAppServices` routes that through `src/test/fake-music-network.ts` to the same `FakeMusicClient` a test already seeds.

- **The lyric's subject is a field of its own, shown only while words are being written.** The prompt describes the music; the words over it can be about coming home without the music brief being about coming home. Blank means "the same as the piece", which is what the lyric always followed — so leaving it alone changes nothing. It is rendered only when the roster can sing _and_ the switch is on, and music_lib drops it from the request on the same rule rather than trusting this to stay in step.
